## 관계형 DB 기본 구조

관계형 DB는 데이터를 **2차원 표(릴레이션)** 로 표현.

### 핵심 용어

| 용어 | 설명 | 비유 |
|------|------|------|
| **릴레이션 (Relation)** | 데이터를 표현하는 2차원 테이블 | 테이블 |
| **튜플 (Tuple)** | 릴레이션의 각 행(Row) | 레코드, 행 |
| **속성 (Attribute)** | 릴레이션의 각 열(Column) | 필드, 컬럼 |
| **도메인 (Domain)** | 속성이 가질 수 있는 값의 집합 | 성적: {A,B,C,D,F} |
| **차수 (Degree)** | 속성(열)의 수 | 컬럼 개수 |
| **카디널리티 (Cardinality)** | 튜플(행)의 수 | 행 개수 |
| **스키마 (Schema)** | 릴레이션의 구조 정의 (속성명, 타입) | 테이블 설계도 |
| **인스턴스 (Instance)** | 특정 시점에 릴레이션에 저장된 실제 데이터 | 현재 데이터 |

**예시**

| 학번 | 학생명 | 학과 | 성적 |
|------|--------|------|------|
| 1001 | 김철수 | CS | A |
| 1002 | 이영희 | EE | B |

- 차수(Degree): **4** (열 4개)
- 카디널리티(Cardinality): **2** (행 2개)

### 키(Key) 종류

| 키 | 설명 |
|----|------|
| **슈퍼키 (Super Key)** | 유일성 만족. 최소성 불필요 |
| **후보키 (Candidate Key)** | 유일성 + 최소성 만족. PK 후보 |
| **기본키 (Primary Key)** | 후보키 중 선택. NULL·중복 불가 |
| **대체키 (Alternate Key)** | 후보키 중 PK가 되지 못한 키 |
| **외래키 (Foreign Key)** | 다른 릴레이션의 PK를 참조하는 속성 |

> 포함 관계: 슈퍼키 ⊃ 후보키 ⊃ 기본키

## 뷰 (View)

하나 이상의 테이블로부터 유도된 **가상 테이블**.  
실제 데이터 저장 없이 SELECT 쿼리를 저장한 것.

```sql
CREATE VIEW 학생_성적뷰 AS
SELECT 학번, 학생명, 성적
FROM 학생
WHERE 성적 = 'A';
```

### 특징

| 항목 | 내용 |
|------|------|
| **독립성** | 원본 테이블 구조 변경 시 뷰를 통한 접근 영향 최소화 |
| **보안성** | 특정 컬럼·행만 노출 → 민감 데이터 숨김 |
| **단순성** | 복잡한 쿼리를 뷰로 단순화 |
| **저장** | 쿼리 정의만 저장 (데이터 미저장) |

### 뷰 조작 제한

- **삽입·수정·삭제 불가** 경우:
  - 집계 함수(SUM, COUNT 등) 포함
  - GROUP BY, DISTINCT 포함
  - 여러 테이블 조인
  - 기본키 없는 경우

```sql
DROP VIEW 학생_성적뷰;   -- 뷰 삭제 (원본 데이터 삭제 아님)
```

## SQL 분류

---

### DDL (데이터 정의 언어)

Data Definition Language — DB 구조(스키마) 정의·변경·삭제.  
**AUTO COMMIT** — 별도 COMMIT 불필요.

| 명령어 | 설명 |
|--------|------|
| **CREATE** | 테이블·뷰·인덱스 등 객체 생성 |
| **ALTER** | 테이블 구조 변경 (컬럼 추가·수정·삭제) |
| **DROP** | 객체 삭제 (복구 불가) |
| **TRUNCATE** | 테이블 데이터 전체 삭제 (구조 유지, 복구 불가) |
| **RENAME** | 객체 이름 변경 |

```sql
CREATE TABLE 학생 (
    학번   CHAR(4)     PRIMARY KEY,
    학생명  VARCHAR(20) NOT NULL,
    학과   VARCHAR(30),
    성적   CHAR(1)
);

ALTER TABLE 학생 ADD 이메일 VARCHAR(50);   -- 컬럼 추가
ALTER TABLE 학생 DROP COLUMN 이메일;       -- 컬럼 삭제

DROP TABLE 학생;       -- 테이블 삭제
TRUNCATE TABLE 학생;   -- 데이터만 전체 삭제
```

---

### DML (데이터 조작 언어)

Data Manipulation Language — 데이터 조회·삽입·수정·삭제.  
**COMMIT 필요** (트랜잭션 단위).

| 명령어 | 설명 |
|--------|------|
| **SELECT** | 데이터 조회 |
| **INSERT** | 데이터 삽입 |
| **UPDATE** | 데이터 수정 |
| **DELETE** | 데이터 삭제 (행 단위, 복구 가능) |

```sql
SELECT 학번, 학생명 FROM 학생 WHERE 성적 = 'A' ORDER BY 학번;

INSERT INTO 학생 VALUES ('1003', '박민수', 'CS', 'B');

UPDATE 학생 SET 성적 = 'A' WHERE 학번 = '1003';

DELETE FROM 학생 WHERE 학번 = '1003';
```

> **DELETE vs TRUNCATE**
> - DELETE: DML, 행 단위, WHERE 조건 가능, ROLLBACK 가능
> - TRUNCATE: DDL, 전체 삭제, ROLLBACK 불가, 빠름

---

### DCL (데이터 제어 언어)

Data Control Language — 접근 권한 제어.

| 명령어 | 설명 |
|--------|------|
| **GRANT** | 사용자에게 권한 부여 |
| **REVOKE** | 사용자 권한 회수 |

```sql
GRANT SELECT, INSERT ON 학생 TO 사용자A;
GRANT ALL PRIVILEGES ON 학생 TO 사용자B WITH GRANT OPTION;  -- 권한 재부여 가능

REVOKE INSERT ON 학생 FROM 사용자A;
```

---

### TCL (트랜잭션 제어 언어)

Transaction Control Language — 트랜잭션 관리.

| 명령어 | 설명 |
|--------|------|
| **COMMIT** | 트랜잭션 성공 종료 — 변경사항 영구 반영 |
| **ROLLBACK** | 트랜잭션 취소 — 마지막 COMMIT 시점으로 복원 |
| **SAVEPOINT** | 트랜잭션 내 중간 저장점 설정 |

```sql
BEGIN;
UPDATE 학생 SET 성적 = 'A' WHERE 학번 = '1001';
SAVEPOINT sp1;
DELETE FROM 학생 WHERE 학번 = '1002';
ROLLBACK TO sp1;  -- sp1 이후만 취소 (DELETE 취소, UPDATE 유지)
COMMIT;
```

> **SQL 분류 암기**
> - DDL: CREATE·ALTER·DROP·TRUNCATE·RENAME (자동 커밋)
> - DML: SELECT·INSERT·UPDATE·DELETE (커밋 필요)
> - DCL: GRANT·REVOKE
> - TCL: COMMIT·ROLLBACK·SAVEPOINT

## ERD (개체-관계 다이어그램)

**Entity-Relationship Diagram** — 현실 세계의 데이터를 개체·관계·속성으로 모델링하는 개념적 설계 도구.

---

### ERD 구성 요소

| 요소 | 표기 | 설명 |
|------|------|------|
| **개체 (Entity)** | 사각형 □ | 독립적으로 존재하는 실체. DB의 테이블로 변환 |
| **관계 (Relationship)** | 마름모 ◇ | 개체 간의 연관성 |
| **속성 (Attribute)** | 타원 ○ | 개체나 관계의 특성 |
| **기본키 속성** | 밑줄 타원 | PK가 되는 속성 |
| **다중값 속성** | 이중 타원 | 여러 값을 가질 수 있는 속성 (예: 전화번호 여러 개) |
| **유도 속성** | 점선 타원 | 다른 속성으로 계산 가능한 속성 (예: 나이 = 현재년도 - 생년) |
| **연결선** | 실선 — | 개체·관계·속성 연결 |

**개체 유형**

| 유형 | 설명 |
|------|------|
| **강한 개체 (Strong Entity)** | 독립적으로 존재. 자체 PK 보유 |
| **약한 개체 (Weak Entity)** | 다른 개체에 종속. 이중 사각형 □□ |

---

### 관계 카디널리티

두 개체 간 관계의 **수적 대응** 표현.

| 관계 | 표기 | 설명 | 예시 |
|------|------|------|------|
| **1:1** | 1 — 1 | 양쪽 모두 하나씩 | 직원 — 사원증 |
| **1:N** | 1 — N | 한쪽이 여러 개 | 학과 — 학생 |
| **M:N** | M — N | 양쪽 모두 여러 개 | 학생 — 과목 |

**참여 제약 (Participation Constraint)**

| 종류 | 표기 | 설명 |
|------|------|------|
| **전체 참여** | 이중선 ══ | 모든 개체가 반드시 관계에 참여 |
| **부분 참여** | 단선 — | 일부만 참여 가능 |

---

### ERD → 릴레이션 변환

| 상황 | 변환 규칙 |
|------|---------|
| **강한 개체** | 개체명 테이블, 기본키 속성 → PK |
| **약한 개체** | 강한 개체 PK를 FK로 포함 + 부분키로 복합 PK 구성 |
| **1:1 관계** | 한쪽 테이블에 상대 PK를 FK로 추가 |
| **1:N 관계** | N쪽 테이블에 1쪽 PK를 FK로 추가 |
| **M:N 관계** | 별도 관계 테이블 생성 (양쪽 PK를 복합 PK로) |
| **다중값 속성** | 별도 테이블로 분리 |

**M:N 변환 예시**

```
학생(학번, 학생명)
과목(과목코드, 과목명)
수강(학번 FK, 과목코드 FK, 성적)  ← 관계 테이블, PK: (학번, 과목코드)
```

> **핵심 암기**
> - 개체=사각형 / 관계=마름모 / 속성=타원
> - 1:N → N쪽에 FK 추가
> - M:N → 관계 테이블 별도 생성
> - 약한 개체 = 이중 사각형, 강한 개체 PK 의존

## 무결성 (Integrity)

DB에 저장된 데이터가 **정확하고 일관성 있는 상태**를 유지하도록 보장하는 제약 조건.

---

### 무결성 제약 조건 종류

| 무결성 | 설명 | 예시 |
|--------|------|------|
| **개체 무결성 (Entity)** | 기본키(PK)는 NULL·중복 불가 | 학번은 반드시 존재하고 유일해야 함 |
| **참조 무결성 (Referential)** | 외래키(FK)는 참조 테이블의 PK값이거나 NULL | 수강.학번은 학생.학번에 존재해야 함 |
| **도메인 무결성 (Domain)** | 속성값은 정의된 도메인(타입·범위) 내여야 함 | 성적은 A·B·C·D·F 중 하나 |
| **고유 무결성 (Unique)** | 특정 속성값은 중복 불가 (PK 아닌 경우) | 이메일 주소 중복 불가 |
| **NULL 무결성** | 특정 속성은 NULL 불가 | 학생명은 반드시 입력 |
| **키 무결성 (Key)** | 릴레이션에 최소 하나의 키 존재 | 모든 테이블에 기본키 존재 |

**참조 무결성 위반 시 처리 옵션 (ON DELETE / ON UPDATE)**

| 옵션 | 설명 |
|------|------|
| **RESTRICT** | 참조 중이면 삭제·수정 거부 |
| **CASCADE** | 부모 삭제·수정 시 자식도 연쇄 삭제·수정 |
| **SET NULL** | 부모 삭제·수정 시 자식 FK를 NULL로 설정 |
| **SET DEFAULT** | 부모 삭제·수정 시 자식 FK를 기본값으로 설정 |

## 트랜잭션 (Transaction)

DB의 상태를 변환시키는 **논리적 작업 단위**.  
여러 SQL이 하나의 작업으로 묶여 **전부 성공하거나 전부 실패** 해야 함.

---

### ACID 원칙

| 원칙 | 영문 | 설명 |
|------|------|------|
| **원자성** | Atomicity | 트랜잭션은 전부 실행되거나 전혀 실행되지 않아야 함 (All or Nothing) |
| **일관성** | Consistency | 트랜잭션 전후 DB는 항상 일관된 상태 유지 (무결성 제약 조건 만족) |
| **격리성** | Isolation | 동시 실행 트랜잭션들은 서로 간섭하지 않음 |
| **영속성** | Durability | 커밋된 트랜잭션 결과는 장애 후에도 영구 보존 |

> 암기: **원일격영** / **A-C-I-D**

---

### 트랜잭션 상태

```
활동(Active)
    ↓ 실행 완료
부분 완료(Partially Committed)
    ↓ 커밋 성공        ↓ 오류
완료(Committed)    실패(Failed)
                        ↓ 롤백
                   철회(Aborted)
```

| 상태 | 설명 |
|------|------|
| **활동 (Active)** | 트랜잭션 실행 중 |
| **부분 완료 (Partially Committed)** | 마지막 연산 실행 후, 커밋 전 |
| **완료 (Committed)** | 커밋 성공 — 영구 반영 |
| **실패 (Failed)** | 오류 발생으로 실행 중단 |
| **철회 (Aborted)** | 롤백 완료 — 실행 전 상태로 복원 |

**주요 명령어**

| 명령어 | 설명 |
|--------|------|
| `COMMIT` | 트랜잭션 성공 종료 — 변경사항 영구 저장 |
| `ROLLBACK` | 트랜잭션 취소 — 이전 상태로 복원 |
| `SAVEPOINT` | 트랜잭션 내 중간 저장점 설정 |

---

### 병행제어 기법

여러 트랜잭션 동시 실행 시 **격리성** 보장 — 직렬 가능성(Serializability) 확보.

**동시성 문제**

| 문제 | 설명 |
|------|------|
| **갱신 분실 (Lost Update)** | 두 트랜잭션이 같은 데이터 수정 → 한 쪽 갱신 덮어써짐 |
| **오손 읽기 (Dirty Read)** | 커밋 안 된 데이터를 다른 트랜잭션이 읽음 |
| **반복 불가능 읽기 (Non-Repeatable Read)** | 같은 쿼리 두 번 실행 시 결과 다름 (중간에 수정) |
| **유령 읽기 (Phantom Read)** | 같은 조건 쿼리 두 번 실행 시 새 행 나타남 (중간에 삽입) |

---

#### 로킹 (Locking)

데이터 접근 전 **잠금(Lock)** 획득 → 다른 트랜잭션 접근 제한.

**잠금 종류**

| 종류 | 설명 | 동시 읽기 | 동시 쓰기 |
|------|------|---------|---------|
| **공유 잠금 (S-Lock)** | 읽기 시 설정 | 허용 | 불가 |
| **배타 잠금 (X-Lock)** | 쓰기 시 설정 | 불가 | 불가 |

**잠금 호환성**

| | S-Lock 요청 | X-Lock 요청 |
|-|------------|------------|
| **S-Lock 보유 중** | 허용 | 대기 |
| **X-Lock 보유 중** | 대기 | 대기 |

**2단계 잠금 프로토콜 (2PL, Two-Phase Locking)**
- **확장 단계**: 잠금만 획득, 해제 불가
- **수축 단계**: 잠금만 해제, 획득 불가
- 직렬 가능성 보장 — 단, 교착 상태 발생 가능

**교착 상태 (Deadlock)**
- 두 트랜잭션이 서로의 잠금 해제를 무한 대기
- 예방: 타임스탬프 순서 강제, 선점
- 탐지·회복: 주기적 탐지 후 트랜잭션 하나 강제 롤백

---

#### 타임스탬프 기법

각 트랜잭션에 **시작 시간(타임스탬프)** 부여 → 타임스탬프 순서로 직렬화.

- 잠금 없이 순서 제어 → 교착 상태 없음
- 타임스탬프 위반 시 트랜잭션 **롤백** 후 재시작

| 검사 | 설명 |
|------|------|
| **읽기 규칙** | T(트랜잭션) < W-TS(데이터) 이면 롤백 (더 늦게 쓴 값 읽기 불가) |
| **쓰기 규칙** | T < R-TS 또는 T < W-TS 이면 롤백 |

---

#### 낙관적 병행제어

충돌이 드물다고 **가정** — 잠금 없이 실행 후 커밋 시점에 검증.

1. **읽기 단계**: 잠금 없이 데이터 읽어 로컬 복사본에 수정
2. **검증 단계**: 충돌 여부 확인
3. **쓰기 단계**: 충돌 없으면 커밋, 있으면 롤백

---

**트랜잭션 격리 수준 (Isolation Level)**

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|-----------|-----------|---------------------|-------------|
| **READ UNCOMMITTED** | 발생 | 발생 | 발생 |
| **READ COMMITTED** | 방지 | 발생 | 발생 |
| **REPEATABLE READ** | 방지 | 방지 | 발생 |
| **SERIALIZABLE** | 방지 | 방지 | 방지 |

> 위로 갈수록 동시성↑ 정합성↓ / 아래로 갈수록 동시성↓ 정합성↑

---

### 회복 기법 (Recovery)

장애 발생 시 DB를 일관된 상태로 복원.

- **Undo**: 미완료 트랜잭션 취소 — 변경 전 값으로 복원
- **Redo**: 완료 트랜잭션 재실행 — 변경 후 값으로 재적용
- **검사점(Checkpoint)**: 주기적으로 메모리→디스크 기록. 검사점 이후 로그만 처리

---

#### 즉각 갱신 기법

트랜잭션 실행 **중** 변경사항을 즉시 DB에 반영.

```
실행 중 → 즉시 DB 반영 → 로그 기록
장애 시 → Undo(미완료 취소) + Redo(완료 재실행) 모두 필요
```

- 장점: 커밋 전에도 데이터 반영
- 단점: 장애 시 Undo 처리 복잡

---

#### 지연 갱신 기법

트랜잭션 **커밋 후** 변경사항을 DB에 반영.

```
실행 중 → 로그에만 기록 (DB 미반영) → 커밋 → DB 반영
장애 시 → Redo만 필요 (Undo 불필요)
```

- 장점: 장애 시 처리 단순 (Undo 불필요)
- 단점: 커밋 전까지 실제 반영 지연

**그림자 페이지 기법 (Shadow Paging)**
- 변경 전 페이지의 복사본(그림자) 유지
- 장애 시 그림자 페이지로 복원
- 로그 불필요 — 단, 디스크 공간 많이 사용

> **핵심 암기**
> - 로킹: S-Lock(읽기 공유 가능) / X-Lock(배타적)
> - 2PL: 확장 단계(획득만) → 수축 단계(해제만) → 직렬성 보장
> - 타임스탬프: 잠금 없음, 교착 상태 없음, 위반 시 롤백
> - 즉각 갱신: Undo+Redo 모두 / 지연 갱신: Redo만
> - ACID = 원자성·일관성·격리성·영속성

---

## 인덱스 (Index)

테이블의 특정 컬럼에 대한 **검색 속도 향상**을 위한 별도 자료구조.  
책의 색인과 같은 원리 — 전체 탐색(Full Scan) 없이 빠른 접근.

---

### 인덱스 종류

| 종류 | 설명 |
|------|------|
| **클러스터형 인덱스 (Clustered)** | 인덱스 순서 = 실제 데이터 물리적 저장 순서. 테이블당 1개. PK에 자동 생성 |
| **비클러스터형 인덱스 (Non-Clustered)** | 인덱스와 데이터 물리적 순서 무관. 포인터로 데이터 위치 참조. 여러 개 가능 |
| **유니크 인덱스 (Unique)** | 중복값 허용 안 함. UK 제약 조건에 자동 생성 |
| **복합 인덱스 (Composite)** | 두 개 이상 컬럼으로 구성. 선두 컬럼 순서 중요 |
| **함수 기반 인덱스** | 컬럼에 함수 적용한 결과값으로 인덱스 생성 |

**클러스터형 vs 비클러스터형**

| 구분 | 클러스터형 | 비클러스터형 |
|------|-----------|------------|
| 물리적 정렬 | 인덱스 순서로 정렬됨 | 정렬 없음 |
| 테이블당 개수 | **1개** | **여러 개** |
| 검색 속도 | 범위 검색 빠름 | 단일 조회 빠름 |
| 저장 공간 | 작음 | 추가 공간 필요 |

---

### B-Tree 인덱스

가장 일반적인 인덱스 자료구조. **균형 트리(Balanced Tree)** — 모든 리프 노드가 같은 깊이.

```
          [루트 노드: 50]
         /              \
   [30, 40]           [60, 70]
   /  |   \           /  |   \
[10][35][45]       [55][65][80]  ← 리프 노드 (실제 데이터/포인터)
```

- 루트→리프 탐색: `O(log n)`
- 삽입·삭제 시 균형 유지를 위한 재구성 발생
- **B+Tree**: 리프 노드끼리 연결 → 범위 검색 최적화 (대부분 RDBMS 사용)

---

### 인덱스 설계 원칙

**인덱스 생성 권장**
- WHERE 절에 자주 사용되는 컬럼
- JOIN 조건 컬럼
- ORDER BY, GROUP BY 컬럼
- 카디널리티(중복도)가 낮은 컬럼 (예: 성별 X, 학번 O)

**인덱스 생성 비권장**
- 데이터 변경(INSERT·UPDATE·DELETE)이 매우 빈번한 테이블
- 전체 데이터 대비 조회 비율이 높은 경우 (Full Scan이 오히려 빠름)
- 컬럼 값의 종류가 극히 적은 경우 (성별, 불리언)

```sql
CREATE INDEX idx_학생_학과 ON 학생(학과);           -- 일반 인덱스
CREATE UNIQUE INDEX idx_학생_이메일 ON 학생(이메일); -- 유니크 인덱스
DROP INDEX idx_학생_학과;                           -- 인덱스 삭제
```

> **핵심 암기**
> - 클러스터형 = 물리 정렬, 테이블당 1개 (PK)
> - 비클러스터형 = 포인터 참조, 여러 개 가능
> - B+Tree = 리프 노드 연결 → 범위 검색 최적
> - 카디널리티 낮으면 인덱스 효과 없음

---

## 해싱 기법

키(Key)를 해시 함수에 적용 → 버킷(저장 주소) 직접 계산. 순차 탐색 없이 **O(1)** 접근.

**용어**
- **해시 함수**: 키 → 버킷 주소 변환 함수
- **버킷(Bucket)**: 레코드를 저장하는 기억 공간 단위
- **슬롯(Slot)**: 버킷 내 레코드 1개 저장 공간
- **충돌(Collision)**: 서로 다른 키가 같은 버킷 주소로 매핑
- **오버플로(Overflow)**: 충돌로 버킷이 가득 찬 상태

**해시 함수 종류 (시험 빈출)**

| 기법 | 설명 |
|------|------|
| **제산법 (Division)** | 키를 소수(Prime)로 나눈 **나머지**를 주소로 사용. `h(k) = k mod p` |
| **폴딩법 (Folding)** | 키를 동일 길이 부분으로 나눠 **합산** → 주소 산출. 이동 폴딩·경계 폴딩 |
| **기수 변환법 (Radix)** | 키의 **진수를 변환** (예: 10진→8진) 후 주소 산출 |
| **대수적 코딩법 (Algebraic Coding)** | 키의 각 **비트를 다항식 계수**로 취급 → 다항식 계산으로 주소 산출 |
| **숫자 분석법 (Digit Analysis)** | 키의 각 자리 **분포 분석** → 편중 없는 자리만 선택해 주소 산출 |
| **중간 제곱법 (Mid-Square)** | 키를 **제곱**한 값의 중간 부분을 주소로 사용 |

**충돌 해결 방법**

| 방법 | 설명 |
|------|------|
| **개방 주소법 (Open Addressing)** | 충돌 시 다음 빈 버킷 탐색 (선형·이차·이중 해싱) |
| **체이닝 (Chaining)** | 충돌 시 같은 버킷에 연결 리스트로 연결 |
| **오버플로 구역** | 별도 오버플로 버킷 영역 할당 |

## 분산 데이터베이스

데이터가 **네트워크로 연결된 여러 사이트**에 분산 저장되지만, 사용자에게는 하나의 DB처럼 보이는 시스템.

### 목표 (투명성)

| 투명성 | 설명 |
|--------|------|
| **위치 투명성** | 데이터 저장 위치 몰라도 접근 가능 |
| **중복 투명성** | 데이터 복제 여부 몰라도 사용 가능 |
| **병행 투명성** | 여러 트랜잭션 동시 수행 → 결과 일관성 보장 |
| **장애 투명성** | 일부 사이트 장애 시에도 전체 시스템 동작 |
| **분할 투명성** | 데이터 분할 방식 몰라도 접근 가능 |

### 분할 방식

| 분할 | 설명 | 예시 |
|------|------|------|
| **수평 분할** | 행(튜플) 단위로 여러 사이트에 분산 | 서울 지점 데이터 → 서울 서버, 부산 → 부산 서버 |
| **수직 분할** | 열(속성) 단위로 여러 사이트에 분산 | 기본정보 → A 서버, 급여정보 → B 서버 |
| **혼합 분할** | 수평 + 수직 혼합 | |

### 장단점

| 장점 | 단점 |
|------|------|
| 신뢰성·가용성 향상 | 관리·설계 복잡 |
| 지역 자치성 | 보안 취약 가능 |
| 점진적 확장 용이 | 데이터 일관성 유지 어려움 |
| 응답 속도 향상 (지역 처리) | 통신 오버헤드 발생 |

### CAP 이론

분산 시스템은 세 가지를 **동시에 모두 만족 불가** — 둘만 선택.

| 속성 | 설명 |
|------|------|
| **C (Consistency, 일관성)** | 모든 노드가 같은 시점에 동일한 데이터 |
| **A (Availability, 가용성)** | 모든 요청에 항상 응답 |
| **P (Partition Tolerance, 분할 내성)** | 네트워크 분할 시에도 동작 |

> 실제 분산 시스템: P는 필수 → **CP** 또는 **AP** 선택

## 정규화 (Normalization)

데이터 중복 제거, 삽입·삭제·갱신 이상(Anomaly) 방지를 위해 릴레이션을 분해하는 과정.

### 이상(Anomaly) 종류

| 이상 | 설명 |
|------|------|
| 삽입 이상 | 불필요한 데이터 함께 삽입해야 함 |
| 삭제 이상 | 원하지 않는 데이터까지 삭제됨 |
| 갱신 이상 | 중복 데이터 일부만 수정 시 불일치 발생 |

---

### 정규화 단계

#### 제1정규형 (1NF)
- 모든 속성 값이 **원자값(Atomic Value)**
- 반복 그룹, 다중값 속성 제거

#### 제2정규형 (2NF)
- 1NF 만족
- **완전 함수적 종속** — 기본키 전체에 종속 (부분 함수 종속 제거)
- 기본키가 복합키일 때 일부 컬럼에만 종속되는 속성 분리

#### 제3정규형 (3NF)
- 2NF 만족
- **이행적 함수 종속 제거** — A→B, B→C 이면 A→C 성립하는 것 제거
- 기본키가 아닌 속성 간 종속 제거

#### BCNF (Boyce-Codd Normal Form)
- 3NF 만족
- 모든 결정자가 **후보키** 여야 함
- 3NF보다 강한 조건 — 후보키가 여러 개이고 겹칠 때 적용

#### 제4정규형 (4NF)
- BCNF 만족
- **다치 종속(MVD, Multi-Valued Dependency)** 제거

#### 제5정규형 (5NF)
- 4NF 만족
- **조인 종속(Join Dependency)** 제거
- 무손실 분해 보장

---

### 정규화 단계별 예제 (동일 샘플 사용)

> **시나리오**: 수강신청 시스템  
> 학생이 과목을 수강하고, 교수가 과목을 담당하며, 강의실이 배정됨

---

#### 비정규형 (UNF) — 시작 데이터

| 학번 | 학생명 | 수강정보 (과목코드, 과목명, 담당교수, 강의실, 성적) |
|------|--------|------------------------------------------------------|
| 1001 | 김철수 | (CS101, C언어, 박교수, 101호, A), (CS102, 자바, 이교수, 102호, B) |
| 1002 | 이영희 | (CS101, C언어, 박교수, 101호, B), (CS103, DB, 김교수, 103호, A) |

문제: 수강정보가 다중값 → 원자값 아님

---

#### 1NF — 원자값 분리

| **학번** | **과목코드** | 학생명 | 과목명 | 담당교수 | 강의실 | 성적 |
|----------|-------------|--------|--------|----------|--------|------|
| 1001 | CS101 | 김철수 | C언어 | 박교수 | 101호 | A |
| 1001 | CS102 | 김철수 | 자바 | 이교수 | 102호 | B |
| 1002 | CS101 | 이영희 | C언어 | 박교수 | 101호 | B |
| 1002 | CS103 | 이영희 | DB | 김교수 | 103호 | A |

기본키: **(학번, 과목코드)**

문제점 (부분 함수 종속):
- `학번` → `학생명` (기본키 일부만으로 결정)
- `과목코드` → `과목명, 담당교수, 강의실` (기본키 일부만으로 결정)
- `(학번, 과목코드)` → `성적` (완전 종속 — OK)

#### 2NF — 부분 함수 종속 제거

**학생** 테이블

| **학번** | 학생명 |
|----------|--------|
| 1001 | 김철수 |
| 1002 | 이영희 |

**과목** 테이블

| **과목코드** | 과목명 | 담당교수 | 강의실 |
|-------------|--------|----------|--------|
| CS101 | C언어 | 박교수 | 101호 |
| CS102 | 자바 | 이교수 | 102호 |
| CS103 | DB | 김교수 | 103호 |

**수강** 테이블

| **학번** | **과목코드** | 성적 |
|----------|-------------|------|
| 1001 | CS101 | A |
| 1001 | CS102 | B |
| 1002 | CS101 | B |
| 1002 | CS103 | A |

문제점 (이행적 함수 종속 — 과목 테이블 내):
- `과목코드` → `담당교수` → `강의실`
- 박교수가 강의실 변경 시 CS101 행만 수정 → 갱신 이상

#### 3NF — 이행적 함수 종속 제거

**과목** 테이블 (분리)

| **과목코드** | 과목명 | 담당교수 |
|-------------|--------|----------|
| CS101 | C언어 | 박교수 |
| CS102 | 자바 | 이교수 |
| CS103 | DB | 김교수 |

**교수** 테이블 (신규)

| **담당교수** | 강의실 |
|-------------|--------|
| 박교수 | 101호 |
| 이교수 | 102호 |
| 김교수 | 103호 |

학생/수강 테이블은 그대로 유지.

#### BCNF — 결정자가 후보키 아닌 경우 제거

> **조건 변경**: 한 과목을 여러 교수가 담당 가능, 한 교수는 한 과목만 담당

**수강배정** 테이블 (3NF 상태)

| **학번** | **과목코드** | 담당교수 |
|----------|-------------|----------|
| 1001 | CS101 | 박교수 |
| 1001 | CS102 | 이교수 |
| 1002 | CS101 | 최교수 | ← CS101을 박교수·최교수 둘 다 담당
| 1002 | CS103 | 김교수 |

후보키: `(학번, 과목코드)`, `(학번, 담당교수)`  
함수 종속: `담당교수` → `과목코드` (담당교수는 후보키 아님 → **BCNF 위반**)

분리:

**교수담당** 테이블

| **담당교수** | 과목코드 |
|-------------|----------|
| 박교수 | CS101 |
| 이교수 | CS102 |
| 최교수 | CS101 |
| 김교수 | CS103 |

**학생수강** 테이블

| **학번** | **담당교수** |
|----------|-------------|
| 1001 | 박교수 |
| 1001 | 이교수 |
| 1002 | 최교수 |
| 1002 | 김교수 |

#### 4NF — 다치 종속(MVD) 제거

> **조건 추가**: 학생이 관심 언어와 취미를 각각 여러 개 등록

**학생_정보** 테이블 (BCNF 상태 — 다치 종속 존재)

| **학번** | **관심언어** | **취미** |
|----------|-------------|---------|
| 1001 | Python | 독서 |
| 1001 | Python | 게임 |
| 1001 | Java | 독서 |
| 1001 | Java | 게임 |

`학번 →→ 관심언어`, `학번 →→ 취미` — 독립적 다치 종속 → 조합 폭발

분리:

**학생_관심언어** 테이블

| **학번** | **관심언어** |
|----------|-------------|
| 1001 | Python |
| 1001 | Java |

**학생_취미** 테이블

| **학번** | **취미** |
|----------|---------|
| 1001 | 독서 |
| 1001 | 게임 |

#### 5NF — 조인 종속 제거

> **조건 추가**: 교수가 과목을 담당하고 해당 과목에 교재를 사용

**과목_교수_교재** 테이블 (4NF 상태 — 조인 종속 존재)

| **과목코드** | **담당교수** | **교재** |
|-------------|-------------|---------|
| CS101 | 박교수 | C기초 |
| CS101 | 최교수 | C기초 |
| CS101 | 박교수 | C심화 |
| CS102 | 이교수 | 자바완성 |

세 이진 관계로 무손실 분해:

**과목_교수** 테이블

| 과목코드 | 담당교수 |
|----------|----------|
| CS101 | 박교수 |
| CS101 | 최교수 |
| CS102 | 이교수 |

**과목_교재** 테이블

| 과목코드 | 교재 |
|----------|------|
| CS101 | C기초 |
| CS101 | C심화 |
| CS102 | 자바완성 |

**교수_교재** 테이블

| 담당교수 | 교재 |
|----------|------|
| 박교수 | C기초 |
| 박교수 | C심화 |
| 최교수 | C기초 |
| 이교수 | 자바완성 |

세 테이블 자연조인 시 원본과 동일하게 복원됨 → 무손실 분해 완료

### 정규화 단계 요약 암기표

| 단계 | 핵심 제거 대상 |
|------|---------------|
| 1NF | 원자값 아닌 속성 |
| 2NF | 부분 함수 종속 |
| 3NF | 이행적 함수 종속 |
| BCNF | 결정자가 후보키 아닌 함수 종속 |
| 4NF | 다치 종속 |
| 5NF | 조인 종속 |

---

### 함수적 종속(Functional Dependency)

- **완전 함수 종속**: X→Y에서 X 전체가 Y를 결정
- **부분 함수 종속**: X의 일부만으로도 Y를 결정 (복합키에서 발생)
- **이행적 함수 종속**: X→Y, Y→Z → X→Z (비키 속성이 다른 비키 속성 결정)

---

### 역정규화 (De-normalization)

- 성능 향상 목적으로 정규화된 릴레이션을 의도적으로 합침
- 조인 횟수 감소 → 조회 속도 향상
- 단점: 데이터 중복 증가, 이상 발생 가능성

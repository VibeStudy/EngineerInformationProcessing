## 소프트웨어 검토 기법 (Review Techniques)

**개념**: 개발 산출물의 오류를 조기에 발견하기 위한 동료 검토 방법론

---

### 기법 비교 (시험 빈출)

| 기법 | 주관 | 형식 | 인원 | 핵심 특징 |
|------|------|------|------|-----------|
| **동료검토** | 작성자 | 비공식 | 2~3명 | 가장 간단, 소규모 |
| **워크스루** | 작성자 | 비공식 | 소그룹 | 작성자가 직접 설명·진행 |
| **인스펙션** | 훈련된 중재자 | 공식 | 3~8명 | 가장 체계적, 결함 보고서 작성 |

---

### 동료검토 (Peer Review)

- 작성자가 2~3명 동료에게 직접 설명
- 가장 비공식·간단
- 별도 절차 없음

---

### 워크스루 (Walkthrough)

- 작성자가 회의 주도, 산출물 설명
- 비공식이지만 사전 준비 있음
- 오류 발견 + 개선 아이디어 수집

**절차**:
1. 계획 수립
2. 사전 검토 (참가자 개별 준비)
3. 검토 회의 (작성자 직접 설명)
4. 오류 목록 작성
5. 수정 및 후속 조치

---

### 인스펙션 (Inspection)

- 훈련된 **중재자(Moderator)** 가 주관
- 가장 공식적·체계적
- 결함 데이터 수집 → 보고서 작성 → 품질 지표 활용
- 작성자는 설명 역할만, 중재자가 회의 통제

**역할**:
| 역할 | 설명 |
|------|------|
| 중재자 (Moderator) | 회의 주관, 진행 통제 |
| 작성자 (Author) | 산출물 설명 |
| 검토자 (Reviewer) | 오류 발견 |
| 기록자 (Recorder) | 결함 목록 기록 |

**절차**:
1. 계획 (Planning)
2. 개요 설명 (Overview)
3. 준비 (Preparation)
4. 검토 회의 (Inspection Meeting)
5. 수정 (Rework)
6. 후속 조치 (Follow-up)

---

> **핵심 암기**
> - 동료검토 = 가장 간단, 비공식
> - 워크스루 = 작성자 주도, 비공식
> - 인스펙션 = 중재자 주도, 공식, 가장 체계적

---

## 소프트웨어 아키텍처 패턴

**개념**: 소프트웨어 시스템의 전체 구조를 결정하는 설계 패턴. 반복적으로 나타나는 구조 문제에 대한 검증된 해결책.

---

### 패턴 한눈에 비교 (시험 빈출)

| 패턴 | 핵심 구조 | 대표 사례 |
|------|-----------|-----------|
| **레이어** | 계층 간 단방향 호출 | OSI 7계층, MVC |
| **파이프-필터** | 데이터 단방향 흐름·변환 | Unix 파이프, 컴파일러 |
| **클라이언트-서버** | 요청자/제공자 분리 | 웹 브라우저-웹 서버 |
| **MVC** | Model·View·Controller 역할 분리 | Spring MVC, Django |
| **이벤트 기반** | 이벤트 발생 → 핸들러 처리 | GUI, 메시지 큐 |
| **마이크로서비스** | 독립 배포 가능한 소규모 서비스 집합 | Netflix, 쿠팡 |
| **저장소(Repository)** | 중앙 데이터 저장소 공유 | DB 중심 시스템 |
| **블랙보드** | 여러 모듈이 공유 메모리에 결과 기여 | AI 전문가 시스템 |

---

### 레이어 (Layered Architecture)

- 시스템을 계층으로 분리, 인접 계층끼리만 통신
- 상위 계층 → 하위 계층 단방향 의존

```
[프레젠테이션 계층]
        ↓
[비즈니스 로직 계층]
        ↓
[데이터 접근 계층]
        ↓
[데이터베이스]
```

| 구분 | 내용 |
|------|------|
| **장점** | 계층별 독립 개발·교체, 유지보수 용이 |
| **단점** | 계층 간 데이터 변환 오버헤드, 성능 저하 가능 |

---

### 파이프-필터 (Pipe-Filter)

- 데이터 스트림을 독립 필터들이 순차 변환
- 필터는 서로 상태 공유 없음

```
입력 → [필터1] → 파이프 → [필터2] → 파이프 → [필터3] → 출력
```

| 구성요소 | 설명 |
|----------|------|
| **필터 (Filter)** | 데이터 변환·처리 단위, 독립 동작 |
| **파이프 (Pipe)** | 필터 간 단방향 데이터 전달 통로 |

| 구분 | 내용 |
|------|------|
| **장점** | 재사용성 높음, 필터 교체·추가 용이, 병렬 처리 가능 |
| **단점** | 데이터 변환 오버헤드, 대화형 시스템 부적합 |

**사례**: `ls | grep .txt | sort`, 컴파일러(어휘→구문→의미→코드생성), ETL

---

### 클라이언트-서버 (Client-Server)

- 서비스 요청자(클라이언트)와 제공자(서버) 분리
- 클라이언트가 요청 → 서버가 응답

| 구분 | 내용 |
|------|------|
| **장점** | 서버 중앙 관리, 클라이언트 다수 지원 |
| **단점** | 서버 병목·장애 시 전체 영향, 네트워크 의존 |

---

### MVC (Model-View-Controller)

- 역할을 3개로 분리하여 결합도 낮춤

| 구성요소 | 역할 |
|----------|------|
| **Model** | 데이터·비즈니스 로직 |
| **View** | 화면 표시 (UI) |
| **Controller** | 사용자 입력 처리, Model·View 연결 |

| 구분 | 내용 |
|------|------|
| **장점** | 역할 분리로 유지보수 용이, 뷰 교체 쉬움 |
| **단점** | 구조 복잡, 소규모 프로젝트에 과도 |

---

### 이벤트 기반 (Event-Driven)

- 이벤트 발생 시 등록된 핸들러가 비동기 처리
- 구성요소 간 느슨한 결합

| 구성요소 | 역할 |
|----------|------|
| **이벤트 생성자** | 이벤트 발행 |
| **이벤트 채널** | 이벤트 전달 (큐/버스) |
| **이벤트 소비자** | 이벤트 수신·처리 |

| 구분 | 내용 |
|------|------|
| **장점** | 느슨한 결합, 확장성 높음, 비동기 처리 |
| **단점** | 흐름 추적 어려움, 디버깅 복잡 |

---

### 마이크로서비스 (Microservices)

- 기능별로 독립 배포 가능한 소규모 서비스로 분리
- 서비스 간 API(REST/메시지)로 통신

| 구분 | 내용 |
|------|------|
| **장점** | 독립 배포·확장, 기술 스택 자유, 장애 격리 |
| **단점** | 서비스 간 통신 복잡, 분산 트랜잭션 어려움 |

---

### 저장소 (Repository)

- 모든 구성요소가 중앙 데이터 저장소(DB)를 공유
- 구성요소들은 저장소를 통해 간접 통신

| 구분 | 내용 |
|------|------|
| **장점** | 데이터 일관성 보장, 구성요소 독립 |
| **단점** | 저장소 병목·장애 시 전체 영향 |

---

### 블랙보드 (Blackboard)

- 여러 독립 모듈(지식 소스)이 공유 메모리(블랙보드)에 결과 기여
- 불완전한 정보로 점진적 해결책 도출
- **AI·전문가 시스템**에 주로 사용

| 구성요소 | 역할 |
|----------|------|
| **블랙보드** | 공유 데이터 저장소 |
| **지식 소스** | 독립적 처리 모듈 |
| **제어 모듈** | 어떤 지식 소스 실행할지 결정 |

---

> **핵심 암기**
> - 레이어 = 계층 간 단방향 호출
> - 파이프-필터 = 독립 필터 + 단방향 데이터 흐름
> - 클라이언트-서버 = 요청/응답 분리
> - MVC = Model(데이터) · View(화면) · Controller(제어)
> - 이벤트 기반 = 비동기 · 느슨한 결합
> - 마이크로서비스 = 독립 배포 가능한 소규모 서비스
> - 저장소 = 중앙 DB 공유
> - 블랙보드 = 공유 메모리에 점진적 기여, AI 시스템

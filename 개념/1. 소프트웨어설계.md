## 개발 방법론

### 방법론 비교 (시험 빈출)

| 구분 | 폭포수 기반 | 애자일 |
|------|------------|--------|
| **진행 방식** | 순차적·단계별 | 반복·점진적 |
| **요구사항** | 초기 고정 | 변경 수용 |
| **산출물** | 문서 중심 | 동작하는 소프트웨어 중심 |
| **고객 참여** | 초기·최종 | 지속적 |
| **적합한 상황** | 요구사항 명확·안정적 | 요구사항 변동 잦음 |

---

### 폭포수 모델 (Waterfall)

**개념**: 각 단계를 순서대로 완료 후 다음 단계 진행. 이전 단계로 돌아가기 어려움.

```
요구사항 분석
     ↓
시스템 설계
     ↓
구현 (코딩)
     ↓
테스트
     ↓
유지보수
```

| 구분 | 내용 |
|------|------|
| **장점** | 단계 명확, 문서화 철저, 관리 용이 |
| **단점** | 요구사항 변경 대응 어려움, 후반부에 오류 발견 시 비용 큼 |
| **적합** | 요구사항 확정된 대규모 프로젝트 (정부·금융 시스템) |

---

### 프로토타입 모델 (Prototype)

**개념**: 실제 개발 전 시제품(프로토타입) 제작 → 사용자 피드백 반영 → 본 개발

```
요구사항 → [프로토타입 제작] → 사용자 평가 → 요구사항 정제 → 본 개발
                  ↑__________________________|
```

| 구분 | 내용 |
|------|------|
| **장점** | 요구사항 불명확 시 유용, 사용자 만족도 향상 |
| **단점** | 프로토타입을 최종 산출물로 오해, 관리 어려움 |

---

### 나선형 모델 (Spiral)

**개념**: 계획 → 위험분석 → 개발·검증 → 고객평가를 반복. **위험 관리** 강조.

```
       계획
      ↗    ↘
고객평가    위험분석
      ↖    ↙
     개발·검증
```

각 사이클마다 4단계 반복:
1. **계획** — 목표·대안·제약 결정
2. **위험 분석** — 위험 요소 식별·해결
3. **개발 및 검증** — 산출물 개발·테스트
4. **고객 평가** — 결과 검토·다음 계획

| 구분 | 내용 |
|------|------|
| **장점** | 위험 조기 발견·대응, 대규모 고위험 프로젝트에 적합 |
| **단점** | 모델 복잡, 위험 분석 전문가 필요, 비용 큼 |

---

### 애자일 방법론 (Agile)

**개념**: 짧은 반복 주기(이터레이션)로 동작하는 소프트웨어를 지속 납품. 변화에 유연하게 대응.

**애자일 선언문 4가지 가치**:
1. 프로세스·도구보다 **개인과 상호작용**
2. 포괄적 문서보다 **동작하는 소프트웨어**
3. 계약 협상보다 **고객과의 협력**
4. 계획 준수보다 **변화에 대응**

---

#### 스크럼 (Scrum)

**개념**: 2~4주 단위 스프린트로 제품 기능을 반복 개발하는 프레임워크

**주요 역할**:

| 역할 | 설명 |
|------|------|
| **제품 책임자 (Product Owner)** | 제품 백로그 관리, 우선순위 결정 |
| **스크럼 마스터 (Scrum Master)** | 팀 방해 요소 제거, 프로세스 관리 |
| **개발팀 (Development Team)** | 실제 개발 수행, 자기 조직화 |

**주요 산출물**:

| 산출물 | 설명 |
|--------|------|
| **제품 백로그 (Product Backlog)** | 전체 기능 목록, 우선순위 정렬 |
| **스프린트 백로그 (Sprint Backlog)** | 현재 스프린트에서 처리할 작업 목록 |
| **증분 (Increment)** | 스프린트 완료 시 동작하는 산출물 |

**스크럼 이벤트**:

| 이벤트 | 설명 |
|--------|------|
| **스프린트 계획** | 스프린트 목표·작업 선정 |
| **일일 스크럼** | 매일 15분, 진행 상황 공유 |
| **스프린트 리뷰** | 완성된 증분 시연·검토 |
| **회고 (Retrospective)** | 프로세스 개선 논의 |

---

#### XP (eXtreme Programming)

**개념**: 코드 품질과 변화 대응력 극대화에 집중하는 애자일 기법

**핵심 실천법**:

| 실천법 | 설명 |
|--------|------|
| **페어 프로그래밍** | 2인 1조 코딩, 실시간 코드 리뷰 |
| **TDD (테스트 주도 개발)** | 테스트 먼저 작성 → 코드 구현 |
| **지속적 통합 (CI)** | 코드 변경 시 즉시 빌드·테스트 |
| **리팩토링** | 기능 변경 없이 코드 구조 개선 |
| **소규모 릴리스** | 자주, 작게 배포 |
| **코드 공동 소유** | 모든 팀원이 코드 수정 가능 |

---

#### 칸반 (Kanban)

**개념**: 작업 흐름을 시각화하고 WIP(진행 중 작업 수) 제한으로 흐름 최적화

```
| 할 일 | 진행 중 (WIP≤3) | 완료 |
|--------|-----------------|------|
| 작업A  |     작업C       | 작업E|
| 작업B  |     작업D       |      |
```

| 구분 | 내용 |
|------|------|
| **장점** | 유연함, 스프린트 없음, 즉시 적용 가능 |
| **단점** | 일정 예측 어려움 |

---

> **핵심 암기**
> - 폭포수 = 순차·단계별, 요구사항 고정
> - 프로토타입 = 시제품 먼저, 요구사항 불명확 시 유용
> - 나선형 = 위험 분석 강조, 반복
> - 스크럼 = 스프린트(2~4주) + 백로그 + 3역할
> - XP = 페어프로그래밍·TDD·CI
> - 칸반 = 흐름 시각화 + WIP 제한

## 객체지향 분석 방법론

**개념**: 시스템을 객체 중심으로 분석하는 방법론. 럼바우·부치·야콥슨이 대표적이며 이를 통합하여 UML이 탄생.

---

### 방법론 비교 (시험 빈출)

| 방법론 | 제안자 | 핵심 특징 | 주요 표기법 |
|--------|--------|-----------|-------------|
| **OMT (럼바우)** | Rumbaugh | 객체·동적·기능 3모델로 분석 | 클래스 다이어그램, 상태 다이어그램, DFD |
| **Booch (부치)** | Booch | 설계 중심, 마이크로/매크로 개발 프로세스 | 클래스·객체·상태·상호작용 다이어그램 |
| **OOSE (야콥슨)** | Jacobson | **유스케이스** 중심 분석 | 유스케이스 다이어그램 |
| **UML** | 럼바우+부치+야콥슨 | 위 3가지 통합·표준화 | 13가지 다이어그램 |

---

### 럼바우 분석 (OMT)

3가지 모델로 시스템 분석. 순서: **객체 → 동적 → 기능** (암기: **객동기**)

| 모델 | 표현 도구 | 분석 대상 |
|------|-----------|-----------|
| **객체 모델링** | 클래스 다이어그램 | 정적 구조 — 클래스·속성·관계 |
| **동적 모델링** | 상태 다이어그램 | 상태 변화 — 이벤트·상태·전이 |
| **기능 모델링** | DFD | 데이터 처리 — 입출력·변환 흐름 |

**객체 모델링**
- 클래스·객체 식별, 속성·연산 정의
- 클래스 간 관계: 연관·집합·상속

**동적 모델링**
- 객체 생명주기 표현
- 상태(State) / 이벤트(Event) / 전이(Transition)

**기능 모델링**
- 데이터 변환 과정 표현
- DFD 구성: 프로세스·데이터 흐름·데이터 저장소·외부 엔티티

---

### UML (Unified Modeling Language)

- 럼바우·부치·야콥슨 방법론을 **통합·표준화**한 표기 언어
- OMG(Object Management Group) 표준

**다이어그램 분류**:

| 분류 | 다이어그램 |
|------|-----------|
| **구조 다이어그램** (정적) | 클래스, 객체, 컴포넌트, 배치, 패키지, 복합구조 |
| **행위 다이어그램** (동적) | 유스케이스, 시퀀스, 통신, 상태, 활동, 타이밍, 상호작용개요 |

**빈출 다이어그램**:

| 다이어그램 | 표현 내용 |
|-----------|-----------|
| **클래스** | 클래스·속성·연산·관계 (정적 구조) |
| **유스케이스** | 사용자-시스템 간 기능 상호작용 |
| **시퀀스** | 객체 간 메시지 교환 순서 (시간 흐름) |
| **상태** | 객체의 상태 변화·전이 |
| **활동** | 작업 흐름·조건 분기 (순서도와 유사) |

---

> **핵심 암기**
> - 럼바우(OMT) = 객동기 (객체→동적→기능)
> - UML = 럼바우+부치+야콥슨 통합, OMG 표준
> - 클래스 다이어그램 = 정적 / 시퀀스 = 동적(시간 순서)

## 소프트웨어 아키텍처 패턴

**개념**: 소프트웨어 시스템의 전체 구조를 결정하는 설계 패턴. 반복적으로 나타나는 구조 문제에 대한 검증된 해결책.

---

### 패턴 한눈에 비교 (시험 빈출)

| 패턴 | 핵심 구조 | 대표 사례 |
|------|-----------|-----------|
| **레이어** | 계층 간 단방향 호출 | OSI 7계층, MVC |
| **파이프-필터** | 데이터 단방향 흐름·변환 | Unix 파이프, 컴파일러 |
| **클라이언트-서버** | 요청자/제공자 분리 | 웹 브라우저-웹 서버 |
| **MVC** | Model·View·Controller 역할 분리 | Spring MVC, Django |
| **이벤트 기반** | 이벤트 발생 → 핸들러 처리 | GUI, 메시지 큐 |
| **마이크로서비스** | 독립 배포 가능한 소규모 서비스 집합 | Netflix, 쿠팡 |
| **저장소(Repository)** | 중앙 데이터 저장소 공유 | DB 중심 시스템 |
| **블랙보드** | 여러 모듈이 공유 메모리에 결과 기여 | AI 전문가 시스템 |

### 레이어 (Layered Architecture)

- 시스템을 계층으로 분리, 인접 계층끼리만 통신
- 상위 계층 → 하위 계층 단방향 의존

```
[프레젠테이션 계층]
        ↓
[비즈니스 로직 계층]
        ↓
[데이터 접근 계층]
        ↓
[데이터베이스]
```

| 구분 | 내용 |
|------|------|
| **장점** | 계층별 독립 개발·교체, 유지보수 용이 |
| **단점** | 계층 간 데이터 변환 오버헤드, 성능 저하 가능 |

---

### 파이프-필터 (Pipe-Filter)

- 데이터 스트림을 독립 필터들이 순차 변환
- 필터는 서로 상태 공유 없음

```
입력 → [필터1] → 파이프 → [필터2] → 파이프 → [필터3] → 출력
```

| 구성요소 | 설명 |
|----------|------|
| **필터 (Filter)** | 데이터 변환·처리 단위, 독립 동작 |
| **파이프 (Pipe)** | 필터 간 단방향 데이터 전달 통로 |

| 구분 | 내용 |
|------|------|
| **장점** | 재사용성 높음, 필터 교체·추가 용이, 병렬 처리 가능 |
| **단점** | 데이터 변환 오버헤드, 대화형 시스템 부적합 |

**사례**: `ls | grep .txt | sort`, 컴파일러(어휘→구문→의미→코드생성), ETL

---

### 클라이언트-서버 (Client-Server)

- 서비스 요청자(클라이언트)와 제공자(서버) 분리
- 클라이언트가 요청 → 서버가 응답

| 구분 | 내용 |
|------|------|
| **장점** | 서버 중앙 관리, 클라이언트 다수 지원 |
| **단점** | 서버 병목·장애 시 전체 영향, 네트워크 의존 |

---

### MVC (Model-View-Controller)

- 역할을 3개로 분리하여 결합도 낮춤

| 구성요소 | 역할 |
|----------|------|
| **Model** | 데이터·비즈니스 로직 |
| **View** | 화면 표시 (UI) |
| **Controller** | 사용자 입력 처리, Model·View 연결 |

| 구분 | 내용 |
|------|------|
| **장점** | 역할 분리로 유지보수 용이, 뷰 교체 쉬움 |
| **단점** | 구조 복잡, 소규모 프로젝트에 과도 |

---

### 이벤트 기반 (Event-Driven)

- 이벤트 발생 시 등록된 핸들러가 비동기 처리
- 구성요소 간 느슨한 결합

| 구성요소 | 역할 |
|----------|------|
| **이벤트 생성자** | 이벤트 발행 |
| **이벤트 채널** | 이벤트 전달 (큐/버스) |
| **이벤트 소비자** | 이벤트 수신·처리 |

| 구분 | 내용 |
|------|------|
| **장점** | 느슨한 결합, 확장성 높음, 비동기 처리 |
| **단점** | 흐름 추적 어려움, 디버깅 복잡 |

---

### 마이크로서비스 (Microservices)

- 기능별로 독립 배포 가능한 소규모 서비스로 분리
- 서비스 간 API(REST/메시지)로 통신

| 구분 | 내용 |
|------|------|
| **장점** | 독립 배포·확장, 기술 스택 자유, 장애 격리 |
| **단점** | 서비스 간 통신 복잡, 분산 트랜잭션 어려움 |

---

### 저장소 (Repository)

- 모든 구성요소가 중앙 데이터 저장소(DB)를 공유
- 구성요소들은 저장소를 통해 간접 통신

| 구분 | 내용 |
|------|------|
| **장점** | 데이터 일관성 보장, 구성요소 독립 |
| **단점** | 저장소 병목·장애 시 전체 영향 |

---

### 블랙보드 (Blackboard)

- 여러 독립 모듈(지식 소스)이 공유 메모리(블랙보드)에 결과 기여
- 불완전한 정보로 점진적 해결책 도출
- **AI·전문가 시스템**에 주로 사용

| 구성요소 | 역할 |
|----------|------|
| **블랙보드** | 공유 데이터 저장소 |
| **지식 소스** | 독립적 처리 모듈 |
| **제어 모듈** | 어떤 지식 소스 실행할지 결정 |

---

> **핵심 암기**
> - 레이어 = 계층 간 단방향 호출
> - 파이프-필터 = 독립 필터 + 단방향 데이터 흐름
> - 클라이언트-서버 = 요청/응답 분리
> - MVC = Model(데이터) · View(화면) · Controller(제어)
> - 이벤트 기반 = 비동기 · 느슨한 결합
> - 마이크로서비스 = 독립 배포 가능한 소규모 서비스
> - 저장소 = 중앙 DB 공유
> - 블랙보드 = 공유 메모리에 점진적 기여, AI 시스템

---

## 소프트웨어 검토 기법 (Review Techniques)

**개념**: 개발 산출물의 오류를 조기에 발견하기 위한 동료 검토 방법론

---

### 기법 비교 (시험 빈출)

| 기법 | 주관 | 형식 | 인원 | 핵심 특징 |
|------|------|------|------|-----------|
| **동료검토** | 작성자 | 비공식 | 2~3명 | 가장 간단, 소규모 |
| **워크스루** | 작성자 | 비공식 | 소그룹 | 작성자가 직접 설명·진행 |
| **인스펙션** | 훈련된 중재자 | 공식 | 3~8명 | 가장 체계적, 결함 보고서 작성 |

---

### 동료검토 (Peer Review)

- 작성자가 2~3명 동료에게 직접 설명
- 가장 비공식·간단
- 별도 절차 없음

---

### 워크스루 (Walkthrough)

- 작성자가 회의 주도, 산출물 설명
- 비공식이지만 사전 준비 있음
- 오류 발견 + 개선 아이디어 수집

**절차**:
1. 계획 수립
2. 사전 검토 (참가자 개별 준비)
3. 검토 회의 (작성자 직접 설명)
4. 오류 목록 작성
5. 수정 및 후속 조치

---

### 인스펙션 (Inspection)

- 훈련된 **중재자(Moderator)** 가 주관
- 가장 공식적·체계적
- 결함 데이터 수집 → 보고서 작성 → 품질 지표 활용
- 작성자는 설명 역할만, 중재자가 회의 통제

**역할**:
| 역할 | 설명 |
|------|------|
| 중재자 (Moderator) | 회의 주관, 진행 통제 |
| 작성자 (Author) | 산출물 설명 |
| 검토자 (Reviewer) | 오류 발견 |
| 기록자 (Recorder) | 결함 목록 기록 |

**절차**:
1. 계획 (Planning)
2. 개요 설명 (Overview)
3. 준비 (Preparation)
4. 검토 회의 (Inspection Meeting)
5. 수정 (Rework)
6. 후속 조치 (Follow-up)

---

> **핵심 암기**
> - 동료검토 = 가장 간단, 비공식
> - 워크스루 = 작성자 주도, 비공식
> - 인스펙션 = 중재자 주도, 공식, 가장 체계적

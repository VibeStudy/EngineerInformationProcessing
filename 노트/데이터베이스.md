## DB 개요

### 시스템 카탈로그

* DB 시스템 자체의 정보와 관련이 있는 시스템 데이터베이스. 메타데이터를 저장

* 메타데이터: 시스템 카탈로그에 저장된 정보
  * DB 객체 정보: 테이블, 인덱스, 뷰 등
  * 사용자 정보: 아이디, 패스워드, 접근 권한 등
  * 테이블 무결성 제약 조건 정보: 기본키, 외래키 등
  * 함수, 프로시저, 트리거 등의 정보

* 특징
  * 일반 이용자도 SQL을 사용해 내용 검색 가능
  * DBMS가 스스로 생성 및 유지. 사용자에 의한 갱신 불가능.

## DB 설계

### 개념적 설계

* DBMS 독립적. 현실 세계 데이터를 추상적 개념으로 표현
* ERD (개체-관계 다이어그램) 작성

### 논리적 설계

* 개념적 설계를 특정 DBMS에 맞는 논리적 구조로 변환
* 논리적 데이터베이스 구조로 매핑
* 트랜잭션 인터페이스 설계 
* 관계형 DB 테이블 설계

### 물리적 설계

* 논리적 설계를 실제 저장 구조로 변환. DBMS·하드웨어 의존적
* 데이터베이스 파일의 저장 규모 및 액세스 경로 결정 
* 저장 레코드 양식, 순서, 접근 경로
* 트랜잭션 처리량, 응답 시간, 디스크 용량, 저장공간 효율화 등 고려

### ER 다이어그램

#### 개요

* Entity-Relationship Diagram. 데이터베이스 논리적 설계 단계 산출물
* Peter Chen이 1976년 제안
* 개체(Entity), 속성(Attribute), 관계(Relationship)로 데이터 구조 표현

#### 구성 요소

* **개체(Entity)**: 저장할 데이터 대상. 사각형(`□`)으로 표현
    * 강개체(Strong Entity): 독립적으로 존재 가능
    * 약개체(Weak Entity): 다른 개체에 의존. 이중 사각형(`□□`)으로 표현

* **속성(Attribute)**: 개체의 특성·성질. 타원(`○`)으로 표현
    * 기본 속성: 단순 값
    * 키 속성: 개체 유일 식별. 밑줄 표시
    * 다중값 속성: 값 여러 개 가능. 이중 타원으로 표현
    * 복합 속성: 여러 속성으로 구성
    * 유도 속성: 다른 속성으로 계산 가능. 점선 타원으로 표현

* **관계(Relationship)**: 개체 간 연관. 마름모(`◇`)로 표현
    * 식별 관계: 약개체가 강개체의 키에 의존. 이중 마름모
    * 비식별 관계: 독립적 기본키 보유

#### 관계의 차수(Cardinality)

* **1:1**: 한 개체가 다른 개체 하나와만 대응
* **1:N**: 한 개체가 다른 개체 여러 개와 대응
* **N:M**: 양쪽 개체 모두 여러 개와 대응 → 구현 시 중간 테이블로 분해

#### ERD 표기법

| 표기법 | 특징 |
|--------|------|
| **Chen** | 원조 표기법. 사각형·타원·마름모 사용. 학술적 |
| **IE(Information Engineering)** | 새발(Crow's Foot) 기호로 카디널리티 표현. 실무 多 사용 |
| **Barker** | Oracle 주로 사용. IE와 유사 |

### 정규화

#### 정규화 개요

* 데이터 중복 제거 및 이상(Anomaly) 방지를 위해 릴레이션을 분해하는 과정

* 함수적 종속성(Functional Dependency) 이론 기반

* 정규형 단계가 높을수록 중복 감소, 무결성 향상 — 단, 조인 연산 증가로 성능 저하 가능

**함수적 종속(FD)**: 속성 X 값이 결정되면 속성 Y 값이 유일하게 결정 → `X → Y` (X가 Y를 함수적으로 결정)

---

#### 이상(Anomaly)

정규화가 안 된 테이블에서 발생하는 문제

| 이상 | 설명 |
|------|------|
| 삽입 이상(Insertion Anomaly) | 불필요한 데이터까지 함께 삽입해야 하는 문제 |
| 삭제 이상(Deletion Anomaly) | 일부 데이터 삭제 시 의도치 않은 데이터까지 삭제 |
| 갱신 이상(Update Anomaly) | 중복 데이터 일부만 수정 시 불일치 발생 |

---

#### 정규형

##### 제1정규형 (1NF)

* 모든 속성값이 **원자값(Atomic Value)** — 반복 그룹, 다중값 속성 제거

##### 제2정규형 (2NF)

* 1NF 만족 + **부분 함수 종속 제거**

* 기본키가 복합키일 때, 기본키의 일부에만 종속된 속성을 분리

> 완전 함수 종속: 기본키 전체에 종속

##### 제3정규형 (3NF)

* 2NF 만족 + **이행적 함수 종속 제거**

* 이행 종속: `A → B → C` 관계에서 `A → C` 도출

##### BCNF (Boyce-Codd Normal Form)

* 3NF 강화판

* 모든 결정자(Determinant)가 **후보키**여야 함

* 3NF를 만족해도 BCNF 위반 가능 (후보키가 여러 개, 복합키 중첩 시)

##### 제4정규형 (4NF)

* BCNF 만족 + **다치 종속(Multi-valued Dependency) 제거**

##### 제5정규형 (5NF)

* 4NF 만족 + **조인 종속(Join Dependency) 제거**

**정규형 요약**

| 정규형 | 조건 |
|--------|------|
| 1NF | 원자값 |
| 2NF | 1NF + 부분 함수 종속 제거 |
| 3NF | 2NF + 이행적 종속 제거 |
| BCNF | 3NF + 모든 결정자가 후보키 |
| 4NF | BCNF + 다치 종속 제거 |
| 5NF | 4NF + 조인 종속 제거 |

---

#### 반정규화

* 정규화로 인한 과도한 조인 성능 저하를 해소하기 위해 의도적으로 중복 허용

* 읽기 성능 ↑, 데이터 무결성 관리 부담 ↑

* 방법: 테이블 합병, 중복 컬럼 추가, 파생 속성(계산값 컬럼) 추가

---

#### 정규화 예제

##### 1NF 위반 — 비원자값 존재

| 학번 | 이름 | 수강과목 |
|------|------|----------|
| 001 | 김철수 | 수학, 영어, 과학 |
| 002 | 이영희 | 국어 |

`수강과목` 컬럼에 다중값 → 1NF 위반

**1NF 적용 후**

| 학번 | 이름 | 수강과목 |
|------|------|----------|
| 001 | 김철수 | 수학 |
| 001 | 김철수 | 영어 |
| 001 | 김철수 | 과학 |
| 002 | 이영희 | 국어 |

---

##### 2NF 위반 — 부분 함수 종속

기본키: (학번, 과목코드) 복합키

| 학번 | 과목코드 | 성적 | 학생이름 |
|------|----------|------|----------|
| 001 | C01 | A | 김철수 |
| 001 | C02 | B | 김철수 |
| 002 | C01 | A | 이영희 |

`학생이름`은 `학번`만으로 결정 → 기본키 일부에 종속 → 2NF 위반

**2NF 적용 후** — 분리

| 학번 | 과목코드 | 성적 |
|------|----------|------|
| 001 | C01 | A |
| 001 | C02 | B |
| 002 | C01 | A |

| 학번 | 학생이름 |
|------|----------|
| 001 | 김철수 |
| 002 | 이영희 |

---

##### 3NF 위반 — 이행적 함수 종속

| 학번 | 학과코드 | 학과명 |
|------|----------|--------|
| 001 | D01 | 컴퓨터공학과 |
| 002 | D02 | 전기공학과 |
| 003 | D01 | 컴퓨터공학과 |

`학번 → 학과코드 → 학과명` 이행 종속 → `학과명`이 기본키 아닌 `학과코드`에 종속 → 3NF 위반

**3NF 적용 후** — 분리

| 학번 | 학과코드 |
|------|----------|
| 001 | D01 |
| 002 | D02 |
| 003 | D01 |

| 학과코드 | 학과명 |
|----------|--------|
| D01 | 컴퓨터공학과 |
| D02 | 전기공학과 |

---

##### BCNF 위반 — 결정자가 후보키 아님

수강 테이블. 한 교수는 한 과목만 담당. 학생은 과목당 교수 한 명.

기본키: (학번, 과목명) / 후보키: (학번, 교수명)

| 학번 | 과목명 | 교수명 |
|------|--------|--------|
| 001 | DB | 홍교수 |
| 002 | DB | 홍교수 |
| 001 | OS | 김교수 |

`교수명 → 과목명` 성립 — 교수명이 결정자이나 후보키 아님 → BCNF 위반

**BCNF 적용 후** — 분리

| 교수명 | 과목명 |
|--------|--------|
| 홍교수 | DB |
| 김교수 | OS |

| 학번 | 교수명 |
|------|--------|
| 001 | 홍교수 |
| 002 | 홍교수 |
| 001 | 김교수 |

## 트랜잭션 관리

### 트랜잭션의 상태

* 활성(Active)
  * 트랜잭션이 실행 중인 상태

* 부분 완료(Partially Committed)
  * 마지막 명령문 실행이 끝났지만 아직 Commit 전인 상태

* 완료(Committed)
  * 트랜잭션이 성공적으로 끝나고 변경 내용이 DB에 영구 반영된 상태

* 실패(Failed)
  * 오류나 장애로 트랜잭션 실행을 계속할 수 없는 상태

* 철회(Aborted)
  * 트랜잭션 실패 후 Rollback으로 실행 이전 상태로 되돌린 상태

```
활성 → 부분 완료 → 완료
  ↓
실패 → 철회
```

### 트랜잭션의 특성

* 원자성(Atomicity)
  * 트랜잭션 연산은 모두 수행되거나 모두 수행되지 않아야 함
  * 일부만 실행된 상태는 허용하지 않음

* 일관성(Consistency)
  * 트랜잭션 수행 전후 데이터베이스는 일관된 상태를 유지해야 함
  * 무결성 제약 조건을 위반하지 않아야 함

* 격리성(Isolation)
  * 동시에 실행되는 트랜잭션은 서로 간섭하지 않아야 함
  * 각 트랜잭션은 독립적으로 실행되는 것처럼 보여야 함

* 지속성(Durability)
  * Commit된 결과는 장애가 발생해도 영구적으로 보존되어야 함
  * 회복 기법과 로그를 통해 보장

### 병행 제어 기법

* 여러 트랜잭션을 동시에 실행하면서 데이터베이스 일관성을 유지하는 기법

* 로킹(Locking)
  * 트랜잭션이 데이터에 접근하기 전 잠금을 설정하고 작업 완료 후 해제
  * 다른 트랜잭션의 동시 접근을 제한해 충돌 방지
  * 교착 상태가 발생할 수 있음

* 2단계 로킹(2PL; Two-Phase Locking)
  * 확장 단계: 잠금 획득만 가능하고 해제 불가
  * 축소 단계: 잠금 해제만 가능하고 획득 불가
  * 직렬 가능성을 보장하지만 교착 상태가 발생할 수 있음

* 타임스탬프 순서 기법(Timestamp Ordering)
  * 트랜잭션에 시간표를 부여
  * 시간 순서대로 실행 결과를 검증
  * 오래된 트랜잭션이 최신 데이터에 부적절하게 접근하면 철회
  * 교착 상태는 발생하지 않지만 Rollback 증가 가능

* 낙관적 병행 제어(Optimistic Concurrency Control)
  * 충돌이 적다고 가정하고 먼저 실행한 뒤 검증 단계에서 충돌 여부 확인
  * 읽기 단계 → 검증 단계 → 쓰기 단계 순서로 수행
  * 충돌이 적은 환경에서 효율적

* 다중 버전 병행 제어(MVCC; Multi-Version Concurrency Control)
  * 데이터 여러 버전을 유지해 읽기와 쓰기 충돌을 줄이는 기법
  * 읽기 작업은 이전 버전을 보고 쓰기 작업은 새 버전을 생성
  * 동시성은 높지만 저장 공간과 버전 관리 비용 증가

### 회복

* 트랜잭션 수행 중 장애로 데이터베이스 손상되었을 때 정상 상태로 복구하는 작업

* 검사점 기법(Check point)
  * 트랙잭션 단계별 로그에 기록
  * 장애 발생 시 전체 트랜잭션 철회가 아닌 검사점부터 회복 진행

* 그림자 페이지 대체 기법(Shadow Paging)
  * 갱신 전 데이터 베이스를 페이징 단위로 복제
  * 갱신이 복제한 그림자 페이지 사용
  * 로그, Undo, Redo 불필요

* 연기 갱신 기법(Deferred Update)
  * 갱신 내용 Log에 저장
  * 트랜잭션 성공 직전에 Log에 보관한 내용을 실제 DB에 기록
  * Undo 불필요, Redo 가능

* 즉각 갱신 기법(Immediate Update)
  * 트랜잭션 내용을 바로 실제 DB에 반영
  * 갱신 내용 Log에 보관
  * Redo, Undo 가능

## 데이터베이스 운용

### 파티션

#### 파티션 개요

* 대용량 테이블이나 인덱스를 논리적 단위로 나누는 것
* 데이터 처리는 테이블 단위, 저장은 파티션별로 수행

* 장점
  * 시스템 장애 영향 최소화
  * 쿼리, 디스크, 복구 성능, 데이터 가용성 향상
  * 파티션 단위로 입출력 분산

* 단점
  * 관리의 어려움
  * 작은 테이블 파티셔닝 시 성능 저하
  * 조인 비용 증가

#### 파티션 종류

* 범위 분할: 지정한 열의 값을 기준으로 범위 지정

* 해시 분할
  * 해시 함수를 적용한 결과 값에 따른 분할
  * 데이터가 고르게 분산되어 있을 때 유용
  * 데이터 위치 판단 불가

* 조합 분할
  * 범위 분할 + 해시 분할
  * 범위 분할 파티션이 큰 경우 사용

* 목록 분할
  * 지정한 열 값에 대한 목록 생성
  * ex: 국가라는 열에서 한국, 일본을 묶기 위해 아시아 목록 생성

* 라운드 로빈 분할
  * 레코드 균일 분배
  * 레코드 순차적 분배
  * 기본키 불필요

### 분산 데이터베이스

* 물리적으로 분산된 여러 사이트에 데이터를 저장하고, 네트워크로 연결하여 논리적으로 하나의 DB처럼 운영

#### 분산 DB 목표

| 목표 | 설명 |
|------|------|
| **위치 투명성(Location Transparency)** | 데이터가 어느 사이트에 있는지 몰라도 접근 가능 |
| **중복 투명성(Replication Transparency)** | 데이터가 여러 곳에 복제되어 있어도 단일 데이터처럼 사용 |
| **병행 투명성(Concurrency Transparency)** | 여러 트랜잭션 동시 실행 시 결과 일관성 보장 |
| **장애 투명성(Failure Transparency)** | 일부 사이트 장애 시에도 정상 동작 |
| **분할 투명성(Division Transparency)** | 데이터가 분할 저장되어 있어도 전체로 인식 |

> 투명성 = 사용자가 분산 사실을 **의식하지 않아도 됨**

## SQL

**SQL 명령어 분류**

| 분류 | 명령어 | 설명 |
|------|--------|------|
| DDL | CREATE, ALTER, DROP, TRUNCATE, RENAME | 데이터 구조 정의 |
| DML | SELECT, INSERT, UPDATE, DELETE | 데이터 조작 |
| DCL | GRANT, REVOKE | 접근 권한 제어 |
| TCL | COMMIT, ROLLBACK, SAVEPOINT | 트랜잭션 제어 |

---

### DDL (Data Definition Language)

* 데이터베이스 객체(테이블, 인덱스, 뷰 등) 구조 정의·변경·삭제

* **자동 COMMIT** — 실행 즉시 반영, 롤백 불가

| 명령어 | 설명 |
|--------|------|
| `CREATE` | 객체 생성 |
| `ALTER` | 객체 구조 변경 |
| `DROP` | 객체 삭제 (구조 + 데이터 모두) |
| `TRUNCATE` | 테이블 데이터 전체 삭제 (구조 유지, DELETE보다 빠름) |
| `RENAME` | 객체 이름 변경 |

```sql
-- 테이블 생성
CREATE TABLE 학생 (
    학번   CHAR(10)    PRIMARY KEY,
    이름   VARCHAR(20) NOT NULL,
    학과   VARCHAR(30),
    학년   INT         DEFAULT 1
);

-- 컬럼 추가
ALTER TABLE 학생 ADD 이메일 VARCHAR(50);

-- 컬럼 삭제
ALTER TABLE 학생 DROP COLUMN 이메일;

-- 테이블 삭제
DROP TABLE 학생;

-- 데이터만 전체 삭제 (구조 유지)
TRUNCATE TABLE 학생;
```

---

### DML (Data Manipulation Language)

* 데이터 조회·삽입·수정·삭제

* **자동 COMMIT 아님** — TCL로 트랜잭션 제어 가능

| 명령어 | 설명 |
|--------|------|
| `SELECT` | 데이터 조회 |
| `INSERT` | 데이터 삽입 |
| `UPDATE` | 데이터 수정 |
| `DELETE` | 데이터 삭제 (구조 유지, 롤백 가능) |

```sql
-- 조회
SELECT 이름, 학과 FROM 학생 WHERE 학년 = 2 ORDER BY 이름;

-- 삽입
INSERT INTO 학생 (학번, 이름, 학과, 학년) VALUES ('20240001', '김철수', '컴공', 1);

-- 수정
UPDATE 학생 SET 학년 = 2 WHERE 학번 = '20240001';

-- 삭제
DELETE FROM 학생 WHERE 학번 = '20240001';
```

**SELECT 절 실행 순서**

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

---

### DCL (Data Control Language)

* 사용자 접근 권한 부여·회수

| 명령어 | 설명 |
|--------|------|
| `GRANT` | 권한 부여 |
| `REVOKE` | 권한 회수 |

```sql
-- 권한 부여
GRANT SELECT, INSERT ON 학생 TO user1;

-- 모든 권한 부여
GRANT ALL PRIVILEGES ON 학생 TO user1;

-- 권한 위임 허용 (다른 사용자에게 재부여 가능)
GRANT SELECT ON 학생 TO user1 WITH GRANT OPTION;

-- 권한 회수
REVOKE INSERT ON 학생 FROM user1;
```

## DB 개요 (9)

### 데이터 모델 (3)

* 데이터 모델(Data Model)
  * 현실 세계의 데이터를 컴퓨터가 처리할 수 있도록 단순화·추상화하여 표현한 체계
  * 데이터의 구조, 연산, 제약 조건을 정의함

* 데이터 구조(Data Structure)
  * 데이터의 논리적 구성과 데이터 간 관계를 표현
  * 관계형 모델에서는 릴레이션, 속성, 튜플, 관계 등이 해당

* 데이터 연산(Data Operation)
  * 저장된 데이터를 검색, 삽입, 삭제, 수정하는 방법을 정의
  * 관계형 모델에서는 관계대수, 관계해석, SQL 등이 해당

* 데이터 제약 조건(Data Constraint)
  * 데이터가 지켜야 할 규칙과 허용 범위를 정의
  * 무결성, 도메인, 키, 참조 무결성 등이 해당

* 암기: 데이터 모델 구성 요소 = 구조 → 연산 → 제약 조건

### 용어

* 자료: 발생된 사실 그 자체. 가공되지 않은 상태

* 정보: 데이터를 가공한 것. 주관적 가치 판단 개입.

* 관계형 데이터 모델(Relational Data Model): 데이터를 2차원 테이블인 릴레이션(Relation)으로 표현하는 데이터 모델

* Attribute: 테이블의 열

* Tuple: 테이블의 행

* degree: 하나의 릴레이션에 속성의 전체 개수

* cardinality: 하나의 릴레이션에서 튜플의 전체 개수

### 릴레이션의 특성 (4)

* 속성의 원자성

  * 각 속성 값은 더 이상 분해할 수 없는 원자값이어야 함

* 속성의 무순서성

  * 속성의 순서는 의미가 없으며, 순서가 바뀌어도 릴레이션은 동일함

* 튜플의 유일성

  * 같은 값을 가진 튜플은 중복될 수 없음

* 튜플의 무순서성

  * 튜플의 순서는 의미가 없으며, 순서가 바뀌어도 릴레이션은 동일함

### 뷰(View)의 의미와 특징

* 뷰(View)

  * 하나 이상의 기본 테이블(Base Table)에서 유도한 가상 테이블(Virtual Table)

  * 뷰의 정의만 저장하며, 일반 뷰는 실제 데이터를 별도로 저장하지 않음

* 특징

  * 논리적으로만 존재하는 테이블

  * 뷰에 대한 삽입 수정 삭제 연산은 제한적

  * 다른 뷰를 기반으로 생성 가능

  * 뷰가 정의된 기본 테이블이나 뷰를 삭제하면 관련된 다른 뷰도 삭제

  * 뷰에는 ALTER문 사용 불가능

  * 뷰에 대한 연산은 기본 테이블에 적용된다

### DB의 특징

* 실시간 접근성

* 계속적인 변화

* 동시공유

* 내용에 의한 참조

### DBMS의 장단점

* 장점

  * 데이터 중복 최소화

  * 데이터 공유

  * 데이터 무결성 유지

  * 데이터의 일관성 유지

  * 데이터 보안 보장

  * 응용 프로그램과 데이터의 독립성 유지

  * 표준화의 달성

* 단점

  * 데이터베이스 구축·운영 비용 증대

  * 백업과 복구 과정 복잡

  * 데이터 집약·집중화로 한 부분 오류가 전체 시스템에 영향

  * 데이터베이스 설계 복잡

### 시스템 카탈로그(데이터 사전)

* 시스템 카탈로그(System Catalog) = 데이터 사전(Data Dictionary)

  * 데이터베이스의 구조·정의·제약 조건 등 메타데이터를 저장하는 시스템 데이터베이스

* 메타데이터: 시스템 카탈로그에 저장된 정보

  * DB 객체 정보: 테이블, 인덱스, 뷰 등

  * 사용자 정보: 아이디, 패스워드, 접근 권한 등

  * 테이블 무결성 제약 조건 정보: 기본키, 외래키 등

  * 함수, 프로시저, 트리거 등의 정보

* 데이터 디렉토리(Data Directory)

  * 시스템 카탈로그에 저장된 메타데이터 중 DBMS가 내부적으로 사용하는 정보

  * 데이터의 위치, 저장 구조, 접근 경로 등 DB 운용에 필요한 정보를 저장

  * 사용자가 직접 검색하거나 갱신하지 않음

  * 시스템 카탈로그보다 사용자 접근성이 제한된 내부 관리 정보

* 특징

  * 일반 이용자도 SQL을 사용해 내용 검색 가능

  * DBMS가 스스로 생성 및 유지. 사용자에 의한 갱신 불가능.

### 스키마

* 스키마(Schema)

  * 데이터베이스의 구조, 제약 조건, 데이터 간 관계를 정의한 명세

  * 데이터의 실제 값인 인스턴스(Instance)와 구분됨

* 외부 스키마(External Schema)

  * 사용자가 필요한 데이터베이스의 논리적 구조를 정의

  * aka 서브스키마

* 개념 스키마(Conceptual Schema)

  * 조직에 필요한 데이터베이스의 논리적 구조

  * 하나만 존재

  * 개체 간의 관계와 제약 조건. 데이터베이스의 접근 권한. 보안 및 무결성 규칙에 관한 명세.

* 내부 스키마(Internal Schema)

  * 물리적인 데이터베이스 구조

  * 데이터베이스에 저장될 레코드의 형식. 저장 데이터 항목의 표현 방법. 내부 레코드의 물리적 순서

### 무결성 제약

* 무결성(Integrity)

  * 데이터베이스에 저장된 데이터의 정확성, 일관성, 유효성을 유지하는 성질

* 무결성 제약(Integrity Constraint)

  * 잘못된 데이터 삽입, 수정, 삭제를 방지하기 위해 DBMS가 강제하는 규칙

  * 트랜잭션 수행 전후 데이터베이스가 일관된 상태를 유지하도록 보장

* 개체 무결성(Entity Integrity)

  * 기본키(Primary Key)는 NULL 값을 가질 수 없음

  * 기본키 값은 릴레이션 내에서 중복될 수 없음

  * 각 튜플을 유일하게 식별하기 위한 제약

* 참조 무결성(Referential Integrity)

  * 외래키(Foreign Key)는 참조하는 릴레이션의 기본키 값과 일치해야 함

  * 외래키 값은 참조 대상에 존재하는 값이거나 NULL이어야 함

  * 관련 없는 데이터를 참조하는 현상 방지

* 도메인 무결성(Domain Integrity)

  * 속성 값은 정의된 도메인 범위 안의 값이어야 함

  * 데이터 타입, 길이, 형식, 기본값, 허용 범위 등을 제한

* 사용자 정의 무결성(User-defined Integrity)

  * 업무 규칙에 따라 사용자가 정의하는 제약

  * 예: 재고 수량은 0 이상, 종료일은 시작일보다 늦어야 함

* 키 무결성(Key Integrity)

  * 후보키, 기본키, 대체키 등 키 값은 튜플을 유일하게 식별해야 함

  * 중복된 키 값 허용 불가

* NULL 무결성(NULL Integrity)

  * 특정 속성에 NULL 값 입력을 허용하지 않는 제약

  * 필수 입력 값 보장

* 고유 무결성(Unique Integrity)

  * 특정 속성 값이 릴레이션 내에서 중복되지 않도록 제한

  * 후보키나 대체키 성격의 속성에 사용

* 관계 무결성(Relationship Integrity)

  * 릴레이션 간 관계의 논리적 일관성을 유지하는 제약

  * 참조 무결성을 포함하는 넓은 의미로 사용

```sql
  CREATE TABLE 학생 (
      학번 CHAR(10) PRIMARY KEY,
      이름 VARCHAR(20) NOT NULL,
      이메일 VARCHAR(50) UNIQUE,
      학년 INT DEFAULT 1 CHECK (학년 BETWEEN 1 AND 4),
      학과코드 CHAR(5),
      FOREIGN KEY (학과코드) REFERENCES 학과(학과코드)
  );
```

## DB 설계 (10)

### 개념적 설계

* DBMS 독립적. 현실 세계 데이터를 추상적 개념으로 표현

* ERD (개체-관계 다이어그램) 작성

### 논리적 설계

* 개념적 설계를 특정 DBMS에 맞는 논리적 구조로 변환

* 논리적 데이터베이스 구조로 매핑

* 트랜잭션 인터페이스 설계

* 관계형 DB 테이블 설계

### 물리적 설계

* 논리적 설계를 실제 저장 구조로 변환. DBMS·하드웨어 의존적

* 데이터베이스 파일의 저장 규모 및 액세스 경로 결정

* 저장 레코드 양식, 순서, 접근 경로

* 트랜잭션 처리량, 응답 시간, 디스크 용량, 저장공간 효율화 등 고려

### ER 다이어그램

* 개요

  * Entity-Relationship Diagram. 데이터베이스 논리적 설계 단계 산출물

  * Peter Chen이 1976년 제안

  * 개체(Entity), 속성(Attribute), 관계(Relationship)로 데이터 구조 표현

* 구성 요소

  * Chen 표기 기호

    * 사각형(`□`): 강개체(Strong Entity). 독립적으로 존재하는 개체

    * 이중 사각형(`□□`): 약개체(Weak Entity). 다른 개체에 의존하는 개체

    * 마름모(`◇`): 관계(Relationship). 개체 사이의 연관

    * 이중 마름모(`◇◇`): 식별 관계(Identifying Relationship). 약개체가 강개체의 키에 의존하는 관계

    * 타원(`○`): 일반 속성(Attribute). 개체의 특성·성질

    * 밑줄 타원(`○`): 키 속성(Key Attribute). 개체를 유일하게 식별하는 속성

    * 점선 타원(`○`): 유도 속성(Derived Attribute). 다른 속성으로 계산하는 속성

    * 이중 타원(`◎`): 다중값 속성(Multivalued Attribute). 여러 값을 가질 수 있는 속성

* 관계의 차수(Cardinality)

  * 1:1: 한 개체가 다른 개체 하나와만 대응

  * 1:N: 한 개체가 다른 개체 여러 개와 대응

  * N:M: 양쪽 개체 모두 여러 개와 대응 → 구현 시 중간 테이블로 분해

* ERD 표기법

  * Chen

    * 원조 표기법. 사각형·타원·마름모 사용. 학술적

  * IE(Information Engineering)

    * 새발(Crow's Foot) 기호로 카디널리티 표현. 실무 多 사용

  * Barker

    * Oracle 주로 사용. IE와 유사

### 이상(Anomaly)

* 이상(Anomaly)

  * 정규화가 충분하지 않은 릴레이션에서 데이터 중복으로 인해 발생하는 논리적 문제

  * 삽입, 삭제, 갱신 작업 시 의도하지 않은 부작용이 생김

  * 함수적 종속 관계를 적절히 분리하지 않았을 때 주로 발생

* 삽입 이상(Insertion Anomaly)

  * 새 데이터를 삽입하려면 불필요한 데이터까지 함께 입력해야 하는 문제

  * 일부 속성 값이 아직 없으면 필요한 데이터 자체를 삽입하지 못할 수 있음

  * 예: 학생 정보와 수강 정보가 같은 테이블에 있을 때, 수강 과목이 없는 신입생 정보를 입력하지 못함

* 삭제 이상(Deletion Anomaly)

  * 특정 데이터를 삭제할 때 보존해야 할 데이터까지 함께 삭제되는 문제

  * 예: 학생의 마지막 수강 기록을 삭제했더니 학생 기본 정보까지 사라짐

* 갱신 이상(Update Anomaly)

  * 중복 저장된 데이터 중 일부만 수정되어 데이터 불일치가 발생하는 문제

  * 예: 같은 학과명이 여러 튜플에 반복 저장되어 있을 때 일부 튜플만 수정되어 학과명이 서로 달라짐

* 이상 발생 원인

  * 하나의 릴레이션에 서로 다른 주제의 데이터가 함께 저장됨

  * 부분 함수 종속, 이행적 함수 종속이 제거되지 않음

  * 같은 의미의 데이터가 여러 튜플에 중복 저장됨

* 해결 방법

  * 정규화를 통해 릴레이션을 적절히 분해

  * 데이터 중복을 줄이고 함수적 종속 관계를 명확히 분리

  * 필요 시 기본키와 외래키로 분해된 릴레이션 사이의 참조 무결성 유지

### 정규화 개요

* 데이터 중복 제거 및 이상(Anomaly) 방지를 위해 릴레이션을 분해하는 과정

* 함수적 종속성(Functional Dependency) 이론 기반

* 정규형 단계가 높을수록 중복 감소, 무결성 향상 — 단, 조인 연산 증가로 성능 저하 가능

* 논리적 설계 단계에서 수행된다

* 검색 시간이 증가한다

* 논리적 처리에 영향을 주고 물리적 구조가 바뀌지 않는다

* 함수적 종속(FD; Functional Dependency)

  * 속성 X 값이 결정되면 속성 Y 값이 유일하게 결정되는 관계

  * `X → Y`: X가 Y를 함수적으로 결정

* 결정자(Determinant)

  * 함수적 종속 관계 `X → Y`에서 다른 속성 값을 결정하는 속성

  * 예: `학번 → 이름`에서 학번은 결정자

* 종속자(Dependent)

  * 함수적 종속 관계 `X → Y`에서 결정자에 의해 값이 결정되는 속성

  * 예: `학번 → 이름`에서 이름은 종속자

### 정규화

* 제1정규형(1NF; First Normal Form)

  * 모든 속성값이 원자값(Atomic Value)이어야 함

  * 반복 그룹, 다중값 속성 제거

* 제2정규형(2NF; Second Normal Form)

  * 1NF 만족 + 부분 함수 종속 제거

  * 기본키가 복합키일 때, 기본키의 일부에만 종속된 속성 분리

> 완전 함수 종속: 기본키 전체에 종속

* 제3정규형(3NF; Third Normal Form)

  * 2NF 만족 + 이행적 함수 종속 제거

  * 이행 종속: `A → B → C` 관계에서 `A → C` 도출

* 보이스-코드 정규형(BCNF; Boyce-Codd Normal Form)

  * 3NF 강화판

  * 모든 결정자(Determinant)가 후보키여야 함

  * 3NF를 만족해도 BCNF 위반 가능

  * 후보키가 여러 개이거나 복합키가 중첩될 때 발생 가능

* 제4정규형(4NF; Fourth Normal Form)

  * BCNF 만족 + 다치 종속(Multi-valued Dependency) 제거

* 제5정규형(5NF; Fifth Normal Form)

  * 4NF 만족 + 조인 종속(Join Dependency) 제거

* 정규형 순서

  * 1NF → 2NF → 3NF → BCNF → 4NF → 5NF

  * 1NF: 원자값

  * 2NF: 1NF + 부분 함수 종속 제거

  * 3NF: 2NF + 이행적 종속 제거

  * BCNF: 3NF + 모든 결정자가 후보키

  * 4NF: BCNF + 다치 종속 제거

  * 5NF: 4NF + 조인 종속 제거

## 트랜잭션 관리 (14)

### 트랜잭션의 상태

* 활성(Active)

  * 트랜잭션이 실행 중인 상태

* 부분 완료(Partially Committed)

  * 마지막 명령문 실행이 끝났지만 아직 Commit 전인 상태

* 완료(Committed)

  * 트랜잭션이 성공적으로 끝나고 변경 내용이 DB에 영구 반영된 상태

* 실패(Failed)

  * 오류나 장애로 트랜잭션 실행을 계속할 수 없는 상태

* 철회(Aborted)

  * 트랜잭션 실패 후 Rollback으로 실행 이전 상태로 되돌린 상태

```
  Active → Partially Committed → Committed
    ↓             |
  Failed ←────────┘
    ↓
  Aborted
```

### 트랜잭션의 특성

* 원자성(Atomicity)

  * 트랜잭션 연산은 모두 수행되거나 모두 수행되지 않아야 함

  * 일부만 실행된 상태는 허용하지 않음

* 일관성(Consistency)

  * 트랜잭션 수행 전후 데이터베이스는 일관된 상태를 유지해야 함

  * 무결성 제약 조건을 위반하지 않아야 함

* 격리성(Isolation)

  * 동시에 실행되는 트랜잭션은 서로 간섭하지 않아야 함

  * 각 트랜잭션은 독립적으로 실행되는 것처럼 보여야 함

* 지속성(Durability)

  * Commit된 결과는 장애가 발생해도 영구적으로 보존되어야 함

  * 회복 기법과 로그를 통해 보장

### 병행 제어의 문제점 (4)

* 갱신 분실(Lost Update)

  * 두 트랜잭션이 같은 데이터를 동시에 갱신할 때, 먼저 수행한 갱신 결과가 나중 갱신에 덮어써져 사라지는 문제

* 모순성(Inconsistency)

  * 한 트랜잭션이 여러 데이터를 갱신하는 중 다른 트랜잭션이 일부는 갱신 전, 일부는 갱신 후 값을 읽어 일관되지 않은 결과를 얻는 문제

* 연쇄 복귀(Cascading Rollback)

  * 실패한 트랜잭션이 갱신한 값을 읽은 다른 트랜잭션도 함께 Rollback해야 하는 문제

* 비완료 의존성(Uncommitted Dependency)

  * 다른 트랜잭션이 Commit하지 않은 갱신 결과를 읽는 문제

  * 해당 트랜잭션이 Rollback되면 읽은 값이 무효가 되어 연쇄 복귀가 발생할 수 있음

### 읽기 이상 현상 (3)

* 더티 읽기(Dirty Read)

  * 다른 트랜잭션이 아직 커밋하지 않은 변경값을 읽는 현상

  * 기존 병행 제어 문제점의 비완료 의존성에 해당

  * 상대 트랜잭션이 롤백하면 유효하지 않은 값을 사용하게 됨

* 반복 불가능 읽기(Non-repeatable Read)

  * 하나의 트랜잭션에서 같은 행을 다시 읽을 때, 다른 트랜잭션이 커밋한 수정·삭제 때문에 값이 달라지거나 행이 사라지는 현상

  * 비반복 읽기라고도 하며, 첫 조회와 재조회 사이의 커밋이 핵심

  * 두 조회가 서로 다른 트랜잭션에 속하거나 자기 트랜잭션이 직접 수정해서 값이 바뀐 경우와 구분

* 팬텀 읽기(Phantom Read)

  * 하나의 트랜잭션에서 같은 검색 조건을 다시 실행했을 때, 다른 트랜잭션의 커밋으로 조건을 만족하는 행 집합이 달라지는 현상

  * 삽입·삭제뿐 아니라 기존 행이 조건을 만족하거나 벗어나도록 수정된 경우에도 발생 가능

  * 행 수가 같아도 구성원이 달라지면 팬텀 읽기가 될 수 있음

> 암기: 미커밋 값 읽기 → 더티 읽기. 같은 행의 재조회 결과 변화 → 반복 불가능 읽기. 같은 조건의 행 집합 변화 → 팬텀 읽기.

### 읽기 이상 현상 예제

* 예제 조건

  * T1과 T2는 서로 다른 트랜잭션이며, 각 예제는 독립적

  * 표시된 현상을 허용하는 격리 수준을 전제하며, 실제 실행 결과는 DBMS와 설정에 따라 달라짐

* 더티 읽기 예제

```text
초기 잔액 = 100
T2: BEGIN → 잔액을 200으로 수정, 아직 미커밋
T1: BEGIN → 잔액 조회 결과 200
T2: ROLLBACK → 실제 잔액은 다시 100
T1: 커밋되지 않았던 200을 읽었음
```

* 반복 불가능 읽기 예제

```text
초기 잔액 = 100
T1: BEGIN → 같은 계좌의 잔액 조회 결과 100
T2: BEGIN → 잔액을 200으로 수정 → COMMIT
T1: 같은 계좌의 잔액 재조회 결과 200 → COMMIT
```

* 반복 불가능 읽기 판단

  * T1은 끝나지 않은 같은 트랜잭션 안에서 두 번 조회

  * 두 번째 값 200은 T2가 커밋한 값이므로 더티 읽기는 아님

  * 같은 행의 값이 100 → 200으로 달라졌으므로 반복 불가능 읽기

* 팬텀 읽기 예제

```text
초기 상태: 점수 80 이상인 학생의 학번 집합 = {1, 2}
T1: BEGIN → 점수 80 이상 학생 조회 결과 {1, 2}
T2: BEGIN → 학번 3, 점수 90인 학생 삽입 → COMMIT
T1: 같은 조건으로 재조회한 결과 {1, 2, 3} → COMMIT
```

* 갱신 분실과의 구분

  * 반복 불가능 읽기는 재조회 결과가 달라지는 읽기 문제

  * 갱신 분실은 두 트랜잭션이 같은 이전 값을 바탕으로 계산한 뒤 저장하여 한쪽 변경을 덮어쓰는 쓰기 문제

  * 예: 둘 다 잔액 100을 읽고 각각 10을 더해 110을 저장 → 의도한 120 대신 110이 남음

### 트랜잭션 격리 수준 (4)

* 비교 기준

  * 아래는 SQL 표준의 기본 보장을 학습용으로 요약한 것

  * 허용되는 현상이 반드시 발생한다는 뜻은 아니며, DBMS는 더 강한 보장을 제공할 수 있음

* 미커밋 읽기(Read Uncommitted)

  * 더티 읽기·반복 불가능 읽기·팬텀 읽기를 모두 허용

* 커밋된 읽기(Read Committed)

  * 더티 읽기 방지

  * 반복 불가능 읽기·팬텀 읽기는 허용

* 반복 가능한 읽기(Repeatable Read)

  * 더티 읽기·반복 불가능 읽기 방지

  * 팬텀 읽기까지 방지하도록 요구되지는 않음

* 직렬화 가능(Serializable)

  * 세 읽기 이상 현상을 방지하며, 커밋된 트랜잭션들의 결과가 어떤 직렬 실행 순서와 동등하도록 보장

  * 실제로 트랜잭션을 하나씩만 실행해야 한다는 뜻은 아님

* 암기 순서

  * Read Uncommitted → Read Committed → Repeatable Read → Serializable

  * 기본 보장 증가: 더티 읽기 방지 → 반복 불가능 읽기 추가 방지 → 팬텀 읽기를 포함한 직렬화 이상 방지

* 보장 범위 주의

  * 읽기 이상 세 가지가 없다는 사실만으로 직렬화 가능성이 자동 보장되는 것은 아님

  * PostgreSQL의 Repeatable Read는 팬텀 읽기도 막지만 직렬화 이상은 여전히 가능

> 참고: [PostgreSQL 공식 문서 — 격리 수준과 읽기 이상 현상](https://www.postgresql.org/docs/18/transaction-iso.html)

### 격리 수준과 병행 제어의 관계

* 격리 수준과 구현 기법

  * 격리 수준은 관찰 가능한 동시 실행 결과의 보장이고, 로킹·다중 버전 병행 제어는 이를 구현하는 수단

  * 같은 수준 이름이라도 DBMS와 조회 방식에 따라 실제 동작이 다를 수 있음

* 잠금 유지

  * 잠금 기반 구현은 읽은 행의 공유 잠금을 필요한 기간 유지하여 다른 트랜잭션의 수정·삭제를 제어할 수 있음

  * 기존 행만 잠그는 것으로 새로운 조건 만족 행의 삽입까지 막는다고 단정할 수는 없음

  * 팬텀 방지에는 구현에 따라 키 범위·조건에 대한 제어 등이 필요

* 스냅샷 읽기

  * 일정 시점의 데이터 버전을 조회하여 다른 트랜잭션의 변경 이후에도 같은 이전 값을 읽을 수 있게 함

  * 다중 버전 병행 제어를 사용한다는 사실만으로 반복 불가능 읽기가 항상 방지되지는 않음

  * PostgreSQL의 일반 SELECT는 Read Committed에서 문장마다 스냅샷을 정하고, Repeatable Read에서 첫 데이터 문장 시점의 스냅샷을 유지

* 직렬화와 재시도

  * 충돌을 대기로 조정하거나 직렬화 실패로 트랜잭션을 철회하는 등 구현 방식이 다름

  * 철회된 경우 필요한 재시도는 실패한 문장만이 아니라 트랜잭션 전체를 기준으로 설계

> 참고: [PostgreSQL 공식 문서 — 스냅샷과 직렬화 실패](https://www.postgresql.org/docs/18/transaction-iso.html)

### 병행 제어 기법

* 여러 트랜잭션을 동시에 실행하면서 데이터베이스 일관성을 유지하는 기법

* 로킹(Locking)

  * 트랜잭션이 데이터에 접근하기 전 잠금을 설정하고 작업 완료 후 해제

  * 다른 트랜잭션의 동시 접근을 제한해 충돌 방지

  * 교착 상태가 발생할 수 있음

* 2단계 로킹(2PL; Two-Phase Locking)

  * 확장 단계: 잠금 획득만 가능하고 해제 불가

  * 축소 단계: 잠금 해제만 가능하고 획득 불가

  * 직렬 가능성을 보장하지만 교착 상태가 발생할 수 있음

* 타임스탬프 순서 기법(Timestamp Ordering)

  * 트랜잭션에 시간표를 부여

  * 시간 순서대로 실행 결과를 검증

  * 오래된 트랜잭션이 최신 데이터에 부적절하게 접근하면 철회

  * 교착 상태는 발생하지 않지만 Rollback 증가 가능

* 낙관적 병행 제어(Optimistic Concurrency Control)

  * 충돌이 적다고 가정하고 먼저 실행한 뒤 검증 단계에서 충돌 여부 확인

  * 읽기 단계 → 검증 단계 → 쓰기 단계 순서로 수행

  * 충돌이 적은 환경에서 효율적

* 다중 버전 병행 제어(MVCC; Multi-Version Concurrency Control)

  * 데이터 여러 버전을 유지해 읽기와 쓰기 충돌을 줄이는 기법

  * 읽기 작업은 이전 버전을 보고 쓰기 작업은 새 버전을 생성

  * 동시성은 높지만 저장 공간과 버전 관리 비용 증가

### 회복(Recovery)

* 회복

  * 트랜잭션 실패나 시스템 장애 이후 데이터베이스를 일관된 상태로 복구하는 작업

  * 실패한 작업의 효과 제거는 원자성, 커밋한 작업의 효과 보존은 지속성과 관련

* 그림자 페이지 대체 기법(Shadow Paging)

  * 변경 전 페이지를 가리키는 그림자 페이지 테이블을 유지하고, 변경 페이지는 다른 위치에 기록

  * 커밋 시 새 페이지 테이블을 가리키도록 전환하는 방식이며, 기본 모델에서는 로그 기반 UNDO·REDO를 사용하지 않음

* 즉각 갱신 기법(Immediate Update)

  * 커밋 전에 변경된 데이터 페이지가 저장장치에 기록될 수 있는 방식

  * 전형적인 로그 기반 회복 모델에서는 변경 전·후 정보를 이용해 UNDO·REDO 수행

* 연기 갱신 기법(Deferred Update)

  * 커밋 전에는 변경 내용을 실제 데이터베이스의 영속 페이지에 반영하지 않는 방식

  * 변경 로그를 먼저 남기고 커밋 이후 데이터 페이지 반영을 진행할 수 있음

  * 기본 모델에서는 미커밋 변경의 UNDO가 불필요하며, 커밋 후 미반영 변경의 REDO는 필요할 수 있음

### 선행 기록 로그(WAL)

* 선행 기록 로그(Write-Ahead Logging; WAL)

  * 변경된 데이터 페이지를 영속 저장장치에 기록하기 전에, 해당 변경의 로그를 먼저 영속화하는 원칙

  * 로그를 메모리 버퍼에만 작성한 것으로는 영속화 조건을 충족하지 못함

* 데이터 페이지 기록 순서

  * 변경 로그 영속화 → 해당 변경이 포함된 데이터 페이지 기록

  * 메모리 안에서 데이터 페이지를 수정하기 전 반드시 로그를 디스크에 써야 한다는 뜻은 아님

* 커밋 성공 응답과 지속성

  * 동기식 영속 커밋에서는 커밋 레코드와 그 이전의 필요한 로그를 영속화한 뒤 성공 응답

  * 커밋할 때 수정한 모든 데이터 페이지를 즉시 영속화할 필요는 없음

  * 비동기 커밋 등 영속성 보장을 완화한 설정은 성공 응답 후 장애 시 최근 커밋이 손실될 수 있으므로 구분

* WAL의 역할

  * 로그를 근거로 데이터 페이지에 아직 반영되지 않은 변경을 재적용할 수 있게 함

  * WAL은 기록 순서의 원칙이며, 모든 DBMS가 같은 형식의 로그나 같은 UNDO 절차를 쓴다는 뜻은 아님

> 암기: 데이터 페이지보다 로그 먼저. 커밋 성공 응답 전 필요한 로그 영속화. 커밋과 모든 데이터 페이지 기록은 별개.

> 참고: [PostgreSQL 공식 문서 — WAL 원리](https://www.postgresql.org/docs/18/wal-intro.html)

### 로그·버퍼·로그 순서 번호

* 데이터 버퍼와 더티 페이지(Dirty Page)

  * 데이터 페이지를 메모리에 적재한 뒤 수정하면 저장장치의 내용과 달라진 더티 페이지가 됨

  * 더티 페이지는 미반영 변경이 있다는 뜻이며, 반드시 미커밋 데이터만 포함한다는 뜻은 아님

* 로그 버퍼(Log Buffer)

  * 로그 레코드를 영속 로그 파일에 내보내기 전에 임시 보관하는 메모리 영역

  * 데이터 버퍼와 로그 버퍼는 서로 다른 역할을 수행

* 로그 레코드(Log Record)

  * 트랜잭션 시작·변경·커밋·철회 등 회복에 필요한 정보를 기록

  * 학습용 변경 레코드는 트랜잭션 식별자, 데이터 식별자, 변경 전 값, 변경 후 값으로 표현 가능

  * 실제 기록 내용과 형식은 회복 알고리즘과 DBMS에 따라 다름

* 로그 순서 번호(Log Sequence Number; LSN)

  * 로그 위치와 순서를 식별하는 번호

  * 페이지별 마지막 변경 LSN과 영속 로그의 끝 위치를 이용해 기록 순서와 재적용 필요 여부를 판단하는 구현이 있음

* 개념적 WAL 검사

  * pageLSN이 페이지에 반영된 마지막 변경 로그의 위치이고 flushedLSN이 영속화된 로그의 끝이라고 가정

  * 페이지 기록 전 `flushedLSN >= pageLSN`을 만족시켜 해당 페이지 변경의 로그가 먼저 영속화되도록 함

* 영속화와 단순 쓰기

  * 메모리 버퍼에서 운영체제 캐시로 복사한 것과 전원 장애에도 보존되도록 기록을 완료한 것은 구분

  * 실제 영속성은 DBMS의 동기화 설정과 저장장치의 보장에도 의존

### UNDO·REDO와 장애 회복

* 실행 취소(UNDO)

  * 실패하거나 커밋하지 못한 트랜잭션의 변경 효과를 제거

  * 변경 전 값 100 → 변경 후 값 150이라면 기본적인 값 기반 예제에서 100으로 복구

* 재실행(REDO)

  * 로그를 이용해 필요한 변경을 데이터 페이지에 다시 적용

  * 기본적인 값 기반 예제에서 데이터 페이지가 100으로 남아 있고 커밋한 변경이 150이면 150으로 복구

* 커밋 여부와 페이지 반영 여부

  * 커밋 로그가 영속화되어도 데이터 페이지에는 변경이 아직 반영되지 않았을 수 있음

  * 데이터 페이지에 변경이 기록되어도 그 트랜잭션이 커밋했다는 뜻은 아님

* 학습용 UNDO·REDO 예제

  * 즉각 갱신과 STEAL·NO-FORCE를 사용하는 전통적인 로그 기반 모델을 가정

```text
초기 영속 데이터: X=100, Y=200
T1: X를 150으로 변경 → 변경 로그와 커밋 레코드 영속화
    X 데이터 페이지는 아직 저장장치에 미반영
T2: Y를 250으로 변경 → 변경 로그 영속화
    Y 데이터 페이지는 저장장치에 기록, 아직 미커밋
시스템 장애 발생
회복: T1의 X는 REDO → 150
      T2의 Y는 UNDO → 200
```

* 회복 알고리즘별 차이

  * 위 예제는 개념 설명용이며 모든 DBMS의 실제 장애 회복 순서를 뜻하지 않음

  * ARIES(Algorithms for Recovery and Isolation Exploiting Semantics)는 분석 → REDO → UNDO 순서의 대표적 회복 알고리즘

  * ARIES의 REDO는 이력 반복을 위해 미완료 트랜잭션의 변경도 재현할 수 있고, 이후 UNDO 단계에서 제거

  * 따라서 REDO를 모든 구현에서 커밋된 트랜잭션만 다시 실행하는 절차로 단정하지 않음

> 참고: [CMU 데이터베이스 강의 — ARIES와 회복](https://15445.courses.cs.cmu.edu/spring2023/slides/20-recovery.pdf)

### 버퍼 관리 정책과 회복 (4)

* STEAL

  * 미커밋 트랜잭션의 변경이 있는 페이지도 버퍼에서 내보내 영속 데이터 파일에 기록할 수 있음

  * 전통적인 로그 기반 회복 모델에서는 미커밋 변경 제거를 위한 UNDO가 필요

* NO-STEAL

  * 미커밋 변경이 있는 페이지를 영속 데이터 파일에 기록하지 않음

  * 미커밋 변경이 영속 페이지에 남지 않으므로 기본 모델에서 그 변경에 대한 디스크 UNDO는 불필요

* FORCE

  * 커밋 완료 시 해당 트랜잭션이 변경한 데이터 페이지의 영속화를 강제

  * 커밋 변경의 데이터 페이지 미반영에 대비하는 REDO는 기본 모델에서 불필요

* NO-FORCE

  * 커밋 완료 시 모든 변경 데이터 페이지의 영속화를 강제하지 않음

  * 커밋 후 미반영 변경을 보존하려면 기본 모델에서 REDO가 필요

* 조합별 암기

  * STEAL + NO-FORCE → UNDO·REDO 필요

  * STEAL + FORCE → UNDO 필요

  * NO-STEAL + NO-FORCE → REDO 필요

  * NO-STEAL + FORCE → 기본 모델에서 UNDO·REDO 불필요

> 위 대응은 전통적인 페이지·로그 기반 회복의 학습 모델이다. 다중 버전 구조나 별도 UNDO 저장소를 사용하는 제품에 그대로 대입하지 않음.

> 참고: [CMU 데이터베이스 강의 — STEAL·FORCE와 로그 회복](https://www.cs.cmu.edu/afs/cs/academic/class/15721-f01/www/lectures/recovery_with_aries.pdf)

### 체크포인트와 백업

* 체크포인트(Checkpoint; 검사점)

  * 회복에 필요한 진행 상태 등을 기록하여 장애 후 로그 탐색과 재처리 범위를 줄이는 기법

  * 구현에 따라 더티 페이지 기록을 진행하며, 진행 중 트랜잭션·더티 페이지 정보를 기록할 수 있음

  * 트랜잭션마다 만드는 커밋이나 사용자가 부분 롤백에 사용하는 SAVEPOINT와 구분

* 회복 시작 위치

  * 체크포인트 정보를 바탕으로 필요한 로그 위치를 결정

  * 최신 체크포인트 이후 로그만 보면 항상 충분한 것은 아니며, 이전부터 남은 더티 페이지·진행 중 트랜잭션 정보도 영향을 줌

* 퍼지 체크포인트(Fuzzy Checkpoint)

  * 트랜잭션 처리를 계속하면서 회복에 필요한 상태 정보를 기록하는 방식

  * 체크포인트 순간에 모든 트랜잭션이 끝나거나 모든 더티 페이지가 즉시 영속화된다고 가정하지 않음

* 체크포인트 주기

  * 자주 수행하면 일반적으로 장애 후 회복 작업을 줄일 수 있지만 실행 중 입출력·관리 비용은 증가 가능

* 백업과의 차이

  * 체크포인트는 회복을 돕는 상태 기록이고, 백업은 데이터 복사본을 별도로 보존하는 작업

  * 저장장치가 손실되는 미디어 장애는 로그만으로 해결할 수 있다고 단정할 수 없음

* 시점 복구(Point-in-Time Recovery; PITR)

  * 기준 백업을 복원한 뒤 보관한 로그를 목표 시점까지 재생하는 방식

  * 필요한 백업과 연속된 로그가 확보되어 있어야 함

> 참고: [PostgreSQL 공식 문서 — 체크포인트와 WAL 관리](https://www.postgresql.org/docs/18/wal-configuration.html), [백업과 WAL을 이용한 복구](https://www.postgresql.org/docs/18/wal-intro.html)

## 데이터베이스 운용 (4)

### 파티션 개요

* 대용량 테이블이나 인덱스를 논리적 단위로 나누는 것

* 데이터 처리는 테이블 단위, 저장은 파티션별로 수행

* 장점

  * 시스템 장애 영향 최소화

  * 쿼리, 디스크, 복구 성능, 데이터 가용성 향상

  * 파티션 단위로 입출력 분산

* 단점

  * 관리의 어려움

  * 작은 테이블 파티셔닝 시 성능 저하

  * 조인 비용 증가

### 파티션 종류

* 범위 분할: 지정한 열의 값을 기준으로 범위 지정

* 해시 분할

  * 해시 함수를 적용한 결과 값에 따른 분할

  * 데이터가 고르게 분산되어 있을 때 유용

  * 데이터 위치 판단 불가

* 조합 분할

  * 범위 분할 + 해시 분할

  * 범위 분할 파티션이 큰 경우 사용

* 목록 분할

  * 지정한 열 값에 대한 목록 생성

  * ex: 국가라는 열에서 한국, 일본을 묶기 위해 아시아 목록 생성

* 라운드 로빈 분할

  * 레코드 균일 분배

  * 레코드 순차적 분배

  * 기본키 불필요

### 분산 데이터베이스

* 물리적으로 분산된 여러 사이트에 데이터를 저장하고, 네트워크로 연결하여 논리적으로 하나의 DB처럼 운영

* 분산 DB 목표

  * 위치 투명성(Location Transparency)

    * 데이터가 어느 사이트에 있는지 몰라도 접근 가능

  * 중복 투명성(Replication Transparency)

    * 데이터가 여러 곳에 복제되어 있어도 단일 데이터처럼 사용

  * 병행 투명성(Concurrency Transparency)

    * 여러 트랜잭션 동시 실행 시 결과 일관성 보장

  * 장애 투명성(Failure Transparency)

    * 일부 사이트 장애 시에도 정상 동작

  * 분할 투명성(Division Transparency)

    * 데이터가 분할 저장되어 있어도 전체로 인식

  > 투명성 = 사용자가 분산 사실을 의식하지 않아도 됨

### DB 보안 - 접근 제어

* DB 보안

  * 데이터베이스에 저장된 데이터를 무단 접근, 변조, 삭제, 유출로부터 보호하는 활동

  * 기밀성, 무결성, 가용성 유지를 목표로 함

* 기밀성(Confidentiality)

  * 허가된 사용자만 정보에 접근할 수 있고, 권한이 없는 대상에게 정보가 공개되지 않도록 하는 성질

* 무결성(Integrity)

  * 정보가 허가 없이 변경되거나 훼손되지 않도록 하여 정확성과 완전성을 유지하는 성질

* 가용성(Availability)

  * 허가된 사용자가 필요할 때 정보와 서비스를 이용할 수 있도록 하는 성질

* 접근 제어

  * 사용자별로 데이터 접근 권한을 제한하는 방법

  * DBMS 계정, 역할(Role), 권한(Privilege)을 이용해 허가된 사용자만 데이터에 접근하게 함

  * GRANT로 권한 부여, REVOKE로 권한 회수

* 임의 접근 제어(DAC; Discretionary Access Control)

  * 데이터 소유자가 사용자에게 접근 권한을 부여하거나 회수하는 방식

  * 권한 관리가 유연하지만 권한 전파로 보안 통제가 약해질 수 있음

* 강제 접근 제어(MAC; Mandatory Access Control)

  * 보안 등급과 규칙에 따라 접근을 강제 통제하는 방식

  * 사용자가 임의로 권한을 부여할 수 없음

  * 높은 보안이 필요한 환경에 적합

* 역할 기반 접근 제어(RBAC; Role-Based Access Control)

  * 사용자에게 직접 권한을 주지 않고 역할에 권한을 부여하는 방식

  * 사용자는 배정된 역할을 통해 권한을 획득

  * 조직 단위 권한 관리에 적합

## 관계 데이터 연산 (5)

### 관계대수 정의

* 관계대수(Relational Algebra)

  * 관계형 데이터베이스에서 원하는 데이터를 얻기 위해 릴레이션을 연산하는 절차적 질의 언어

  * 연산의 순서와 방법을 명시

  * 하나 이상의 릴레이션을 입력으로 받아 새로운 릴레이션을 결과로 반환

  * 결과도 릴레이션이므로 다른 연산의 입력으로 사용할 수 있음 → 폐쇄성

* 연산자 분류

  * 순수 관계 연산자: 셀렉트 → 프로젝트 → 조인 → 디비전

  * 일반 집합 연산자: 합집합 → 교집합 → 차집합 → 카티션 프로덕트

### 순수 관계 연산자 (4)

* 관계형 데이터 모델을 위해 새로 정의된 연산자

* 셀렉트(Select; σ)

  * 조건을 만족하는 튜플을 선택

  * 예: 학생 릴레이션에서 학년이 3인 튜플 검색

```text
  학생
  (1, 김철수, 3)
  (2, 이영희, 2)
  (3, 박민수, 3)

  σ 학년=3 (학생)
  → (1, 김철수, 3)
  → (3, 박민수, 3)
```

* 프로젝트(Project; π)

  * 원하는 속성만 선택

  * 예: 학생 릴레이션에서 이름 속성만 검색

```text
  학생
  (1, 김철수, 3)
  (2, 이영희, 2)

  π 이름 (학생)
  → (김철수)
  → (이영희)
```

* 조인(Join; ⋈)

  * 공통 속성을 기준으로 릴레이션을 결합

  * 예: 학생 릴레이션과 학과 릴레이션을 학과코드로 결합

```text
  학생
  (1, 김철수, C01)
  (2, 이영희, C02)

  학과
  (C01, 컴퓨터공학과)
  (C02, 전기공학과)

  학생 ⋈ 학과
  → (1, 김철수, C01, 컴퓨터공학과)
  → (2, 이영희, C02, 전기공학과)
```

* 디비전(Division; ÷)

  * 특정 조건을 모두 만족하는 튜플을 검색

  * 예: 모든 필수 과목을 수강한 학생 검색

```text
  수강
  (김철수, DB)
  (김철수, OS)
  (이영희, DB)

  필수과목
  (DB)
  (OS)

  수강 ÷ 필수과목
  → (김철수)
```

### 일반 집합 연산자 (4)

* 수학의 집합 연산을 릴레이션에 적용한 연산자

* 예제 릴레이션

  * R(학번) = {(1), (2)}, S(학번) = {(2), (3)}

  * 합병 가능 조건: 속성 개수가 같고, 대응하는 속성의 도메인이 같아야 함

* 합집합(Union; ∪)

  * 두 릴레이션의 튜플을 합침

  * 두 릴레이션은 합병 가능해야 함

  * 예: R ∪ S = {(1), (2), (3)} → 중복 튜플 (2)는 한 번만 포함

* 교집합(Intersection; ∩)

  * 두 릴레이션에 공통으로 존재하는 튜플 검색

  * 두 릴레이션은 합병 가능해야 함

  * 예: R ∩ S = {(2)}

* 차집합(Difference; -)

  * 한 릴레이션에는 있고 다른 릴레이션에는 없는 튜플 검색

  * 두 릴레이션은 합병 가능해야 함

  * 예: R − S = {(1)}, S − R = {(3)} → 연산 순서에 따라 결과가 달라짐

* 카티션 프로덕트(Cartesian Product; ×)

  * 두 릴레이션의 모든 튜플 조합 생성

  * 결과 릴레이션의 차수는 두 릴레이션 차수의 합

  * 결과 릴레이션의 카디널리티는 두 릴레이션 카디널리티의 곱

```text
  R × S
  (R.학번, S.학번)
  (1, 2)
  (1, 3)
  (2, 2)
  (2, 3)

  차수: 1 + 1 = 2
  카디널리티: 2 × 2 = 4
```

### 관계해석

* 관계해석(Relational Calculus)

  * 원하는 데이터의 조건을 논리식으로 표현하는 비절차적 질의 언어

  * 원하는 결과를 명시하고 처리 방법은 명시하지 않음

  * 수학의 술어 해석(Predicate Calculus, 프레디킷 해석)에 기반

* 술어(Predicate)

  * 변수의 값에 따라 참·거짓이 결정되는 조건식

  * 예: `t.학년 = 3`은 튜플 t의 학년이 3인지 판단하는 조건

* 종류

  * 튜플 관계해석(Tuple Relational Calculus): 변수가 튜플 전체를 나타냄

  * 도메인 관계해석(Domain Relational Calculus): 변수가 개별 속성 값을 나타냄

* 사용 기호

  * 전칭 한정자 `∀`: 모든 것에 대하여(For All)

  * 존재 한정자 `∃`: 적어도 하나가 존재(There Exists)

  * 논리곱 `∧`: 그리고(AND)

  * 논리합 `∨`: 또는(OR)

  * 부정 `¬`: 아니다(NOT)

  * 포함 `∈`: 집합에 속함

  * 비포함 `∉`: 집합에 속하지 않음

  * 비교 `=`, `≠`, `<`, `≤`, `>`, `≥`: 값의 비교

## SQL (8)

### SQL 명령어 분류

* DDL

  * 명령어: CREATE, ALTER, DROP, TRUNCATE, RENAME

  * 설명: 데이터 구조 정의

* DML

  * 명령어: SELECT, INSERT, UPDATE, DELETE

  * 설명: 데이터 조작

* DCL

  * 명령어: GRANT, REVOKE

  * 설명: 접근 권한 제어

* TCL

  * 명령어: COMMIT, ROLLBACK, SAVEPOINT

  * 설명: 트랜잭션 제어

### DDL (Data Definition Language)

* 데이터베이스 객체(테이블, 인덱스, 뷰 등) 구조 정의·변경·삭제

* 자동 COMMIT — 실행 즉시 반영, 롤백 불가

* `CREATE`

  * 객체 생성

* `ALTER`

  * 객체 구조 변경

* `DROP`

  * 객체 삭제 (구조 + 데이터 모두)

* `TRUNCATE`

  * 테이블 데이터 전체 삭제 (구조 유지, DELETE보다 빠름)

* `RENAME`

  * 객체 이름 변경

```sql
  -- 테이블 생성
  CREATE TABLE 학생 (
      학번   CHAR(10)    PRIMARY KEY,
      이름   VARCHAR(20) NOT NULL,
      학과   VARCHAR(30),
      학년   INT         DEFAULT 1
  );

  -- 컬럼 추가
  ALTER TABLE 학생 ADD 이메일 VARCHAR(50);

  -- 컬럼 삭제
  ALTER TABLE 학생 DROP COLUMN 이메일;

  -- 테이블 삭제
  DROP TABLE 학생;

  -- 데이터만 전체 삭제 (구조 유지)
  TRUNCATE TABLE 학생;
```

### DML (Data Manipulation Language)

* 데이터 조회·삽입·수정·삭제

* 자동 COMMIT 아님 — TCL로 트랜잭션 제어 가능

* `SELECT`

  * 데이터 조회

* `INSERT`

  * 데이터 삽입

* `UPDATE`

  * 데이터 수정

* `DELETE`

  * 데이터 삭제 (구조 유지, 롤백 가능)

```sql
  -- 조회
  SELECT 이름, 학과 FROM 학생 WHERE 학년 = 2 ORDER BY 이름;

  -- 삽입
  INSERT INTO 학생 (학번, 이름, 학과, 학년) VALUES ('20240001', '김철수', '컴공', 1);

  -- 수정
  UPDATE 학생 SET 학년 = 2 WHERE 학번 = '20240001';

  -- 삭제
  DELETE FROM 학생 WHERE 학번 = '20240001';
```

* SELECT 절 실행 순서

```
  FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

### 집계 함수

* 집계 함수

  * 여러 행의 값을 하나의 결과값으로 요약하는 함수

  * `GROUP BY`와 함께 사용하면 그룹별 집계 가능

* COUNT

  * 행이나 컬럼 값의 개수를 계산하는 집계 함수

* `COUNT(*)`

  * 조건에 맞는 전체 행 수를 계산

  * 특정 컬럼 값이 NULL이어도 행 개수에 포함

* `COUNT(컬럼)`

  * 지정한 컬럼 값이 NULL이 아닌 행만 계산

  * NULL 값은 개수에서 제외

* SUM

  * 숫자 컬럼 값의 합계를 계산

  * NULL 값은 제외하고 계산

* AVG

  * 숫자 컬럼 값의 평균을 계산

  * NULL 값은 제외하고 계산

* MAX

  * 컬럼 값 중 최댓값을 계산

* MIN

  * 컬럼 값 중 최솟값을 계산

```text
  학생
  +------+--------+----------+------+
  | 학번 | 이름   | 학과코드 | 점수 |
  +------+--------+----------+------+
  | 1    | 김철수 | C01      | 90   |
  | 2    | 이영희 | C02      | 80   |
  | 3    | 박민수 | NULL     | NULL |
  +------+--------+----------+------+
```

```sql
  SELECT COUNT(*) FROM 학생;
  -- 결과: 3

  SELECT COUNT(학과코드) FROM 학생;
  -- 결과: 2

  SELECT SUM(점수) FROM 학생;
  -- 결과: 170

  SELECT AVG(점수) FROM 학생;
  -- 결과: 85

  SELECT MAX(점수) FROM 학생;
  -- 결과: 90

  SELECT MIN(점수) FROM 학생;
  -- 결과: 80
```

> `COUNT(*)`는 행 수, `COUNT(컬럼)`은 NULL이 아닌 값 수. `SUM`, `AVG`, `MAX`, `MIN`도 NULL 값은 제외하고 계산

### 집합 연산 (4)

* 집합 연산

  * 두 SELECT 문의 조회 결과를 결합하는 연산

  * 양쪽 결과의 열 개수가 같고, 같은 위치의 열끼리 자료형이 호환되어야 함

  * 중복 여부는 선택한 열 전체의 값으로 판단

  * 집합 연산은 조회 결과끼리 결합하고, 조인은 조건에 따라 테이블의 행을 연결

* 공통 예제 데이터

```text
  수강A(학번): (1), (2)
  수강B(학번): (2), (3)
```

* UNION

  * 두 조회 결과를 합치고 중복 행 제거

```sql
  SELECT 학번 FROM 수강A
  UNION
  SELECT 학번 FROM 수강B;
  -- 결과: (1), (2), (3)
```

* UNION ALL

  * 두 조회 결과를 합치고 중복 행도 유지

```sql
  SELECT 학번 FROM 수강A
  UNION ALL
  SELECT 학번 FROM 수강B;
  -- 결과: (1), (2), (2), (3)
```

* INTERSECT

  * 양쪽 조회 결과에 공통으로 존재하는 행만 반환하고 중복 제거

  * 관계대수의 교집합(Intersection)에 대응하는 SQL 키워드는 INTERSECT

```sql
  SELECT 학번 FROM 수강A
  INTERSECT
  SELECT 학번 FROM 수강B;
  -- 결과: (2)
```

* EXCEPT

  * 앞쪽 조회 결과에서 뒤쪽 조회 결과에 있는 행을 제외하고 중복 제거

  * 순서를 바꾸면 결과도 달라질 수 있음

```sql
  SELECT 학번 FROM 수강A
  EXCEPT
  SELECT 학번 FROM 수강B;
  -- 결과: (1)
  -- 반대로 수강B EXCEPT 수강A를 조회하면 (3)
```

> 예제 결과의 나열 순서는 설명용. 실제 출력 순서는 ORDER BY가 없으면 보장되지 않음.

> DBMS와 버전에 따라 지원 문법이 다를 수 있음. Oracle의 차집합 문법으로는 MINUS도 사용.

### 조인

* 조인(Join)

  * 두 개 이상의 테이블을 공통 속성이나 조건을 기준으로 연결하여 데이터를 조회하는 연산

  * 정규화로 분리된 테이블의 관련 데이터를 함께 조회할 때 사용

* 예제 테이블

```text
  학생
  +------+--------+----------+
  | 학번 | 이름   | 학과코드 |
  +------+--------+----------+
  | 1    | 김철수 | C01      |
  | 2    | 이영희 | C02      |
  | 3    | 박민수 | NULL     |
  +------+--------+----------+

  학과
  +----------+----------+
  | 학과코드 | 학과명   |
  +----------+----------+
  | C01      | 컴퓨터   |
  | C02      | 전자     |
  | C03      | 기계     |
  +----------+----------+
```

* 내부 조인(Inner Join)

  * 조인 조건을 만족하는 행만 조회

  * 두 테이블 모두에 일치하는 값이 있는 데이터만 결과에 포함

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생
  INNER JOIN 학과
  ON 학생.학과코드 = 학과.학과코드;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 이영희 | 전자   |
  +--------+--------+
```

* 왼쪽 외부 조인(Left Outer Join)

  * 왼쪽 테이블의 모든 행을 조회하고, 오른쪽 테이블은 조건에 맞는 행만 연결

  * 오른쪽 테이블에 일치하는 값이 없으면 NULL로 표시

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생
  LEFT OUTER JOIN 학과
  ON 학생.학과코드 = 학과.학과코드;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 이영희 | 전자   |
  | 박민수 | NULL   |
  +--------+--------+
```

* 오른쪽 외부 조인(Right Outer Join)

  * 오른쪽 테이블의 모든 행을 조회하고, 왼쪽 테이블은 조건에 맞는 행만 연결

  * 왼쪽 테이블에 일치하는 값이 없으면 NULL로 표시

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생
  RIGHT OUTER JOIN 학과
  ON 학생.학과코드 = 학과.학과코드;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 이영희 | 전자   |
  | NULL   | 기계   |
  +--------+--------+
```

* 완전 외부 조인(Full Outer Join)

  * 양쪽 테이블의 모든 행을 조회

  * 한쪽에만 존재하는 데이터는 반대쪽 속성을 NULL로 표시

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생
  FULL OUTER JOIN 학과
  ON 학생.학과코드 = 학과.학과코드;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 이영희 | 전자   |
  | 박민수 | NULL   |
  | NULL   | 기계   |
  +--------+--------+
```

* 교차 조인(Cross Join)

  * 두 테이블의 모든 행 조합을 생성

  * 결과 행 수 = 첫 번째 테이블 행 수 × 두 번째 테이블 행 수

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생
  CROSS JOIN 학과;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 김철수 | 전자   |
  | 김철수 | 기계   |
  | 이영희 | 컴퓨터 |
  | 이영희 | 전자   |
  | 이영희 | 기계   |
  | 박민수 | 컴퓨터 |
  | 박민수 | 전자   |
  | 박민수 | 기계   |
  +--------+--------+
```

* 자기 조인(Self Join)

  * 같은 테이블을 두 번 사용하여 자기 자신과 조인

  * 같은 테이블 안의 계층 관계나 비교 관계를 조회할 때 사용

```sql
  SELECT 사원.이름, 관리자.이름 AS 관리자명
  FROM 사원
  INNER JOIN 사원 AS 관리자
  ON 사원.관리자번호 = 관리자.사원번호;
```

```text
  사원
  +----------+--------+------------+
  | 사원번호 | 이름   | 관리자번호 |
  +----------+--------+------------+
  | 1        | 김부장 | NULL       |
  | 2        | 이대리 | 1          |
  | 3        | 박사원 | 2          |
  +----------+--------+------------+

  결과
  +--------+----------+
  | 이름   | 관리자명 |
  +--------+----------+
  | 이대리 | 김부장   |
  | 박사원 | 이대리   |
  +--------+----------+
```

* 자연 조인(Natural Join)

  * 두 테이블에서 이름이 같은 속성을 자동으로 기준 삼아 조인

  * 같은 이름의 속성이 의도와 다르면 잘못된 결과가 나올 수 있음

```sql
  SELECT *
  FROM 학생
  NATURAL JOIN 학과;
```

```text
  +----------+------+--------+--------+
  | 학과코드 | 학번 | 이름   | 학과명 |
  +----------+------+--------+--------+
  | C01      | 1    | 김철수 | 컴퓨터 |
  | C02      | 2    | 이영희 | 전자   |
  +----------+------+--------+--------+
```

* 동등 조인(Equi Join)

  * 조인 조건에 `=` 연산자를 사용하는 조인

  * 내부 조인의 가장 일반적인 형태

```sql
  SELECT 학생.이름, 학과.학과명
  FROM 학생, 학과
  WHERE 학생.학과코드 = 학과.학과코드;
```

```text
  +--------+--------+
  | 이름   | 학과명 |
  +--------+--------+
  | 김철수 | 컴퓨터 |
  | 이영희 | 전자   |
  +--------+--------+
```

* 비동등 조인(Non-Equi Join)

  * 조인 조건에 `=`, 이외의 비교 연산자(`<`, `>`, `BETWEEN` 등)를 사용하는 조인

  * 범위 비교가 필요한 경우 사용

```sql
  SELECT 학생.이름, 성적등급.등급
  FROM 학생
  INNER JOIN 성적등급
  ON 학생.점수 BETWEEN 성적등급.최소점수 AND 성적등급.최대점수;
```

```text
  점수 포함 학생
  +--------+------+
  | 이름   | 점수 |
  +--------+------+
  | 김철수 | 95   |
  | 이영희 | 82   |
  | 박민수 | 71   |
  +--------+------+

  성적등급
  +------+----------+----------+
  | 등급 | 최소점수 | 최대점수 |
  +------+----------+----------+
  | A    | 90       | 100      |
  | B    | 80       | 89       |
  | C    | 70       | 79       |
  +------+----------+----------+

  결과
  +--------+------+
  | 이름   | 등급 |
  +--------+------+
  | 김철수 | A    |
  | 이영희 | B    |
  | 박민수 | C    |
  +--------+------+
```

### DCL (Data Control Language)

* 사용자 접근 권한 부여·회수

* `GRANT`

  * 권한 부여

* `REVOKE`

  * 권한 회수

```sql
  -- 권한 부여
  GRANT SELECT, INSERT ON 학생 TO user1;

  -- 모든 권한 부여
  GRANT ALL PRIVILEGES ON 학생 TO user1;

  -- 권한 위임 허용 (다른 사용자에게 재부여 가능)
  GRANT SELECT ON 학생 TO user1 WITH GRANT OPTION;

  -- 권한 회수
  REVOKE INSERT ON 학생 FROM user1;
```

### 트리거

* 트리거(Trigger)

  * 데이터베이스에서 지정한 이벤트가 발생할 때 관련 작업을 자동으로 수행하는 절차형 SQL

  * 대표적인 실행 이벤트는 테이블의 `INSERT`, `UPDATE`, `DELETE`

  * 사용자가 직접 호출하지 않고, 미리 정의한 이벤트에 의해 자동 실행됨

* 구성 요소

  * 이벤트(Event): 트리거를 실행시키는 데이터 삽입·수정·삭제 등의 작업

  * 조건(Condition): 트리거의 작업을 수행할지 판단하는 조건

  * 동작(Action): 이벤트 발생 시 실행할 SQL 작업

* 실행 시점

  * `BEFORE`: 데이터 변경 전에 실행. 입력값 검사·보정 등에 사용

  * `AFTER`: 데이터 변경 후에 실행. 변경 이력 기록·관련 데이터 갱신 등에 사용

  * 지원하는 실행 시점과 문법은 데이터베이스 관리 시스템(DBMS; Database Management System)에 따라 다름

* 실행 단위

  * 행 수준 트리거: 영향을 받는 각 행마다 실행

  * 문장 수준 트리거: SQL 문장 하나에 대해 한 번 실행

  * MySQL은 행 수준 트리거를 지원하며 `FOR EACH ROW`로 지정

* 활용

  * 데이터 변경 이력을 자동으로 기록

  * 업무 규칙에 따른 데이터 검증 및 무결성 유지

  * 원본 데이터 변경에 따른 집계 데이터 갱신

* 프로시저·옵티마이저와의 구분

  * 저장 프로시저(Stored Procedure): 미리 저장한 SQL 작업을 명시적인 호출로 실행

  * 트리거: 지정한 이벤트가 발생하면 자동 실행

  * 옵티마이저(Optimizer): SQL의 효율적인 실행 계획을 선택하는 모듈

* MySQL 예제

  * `학생(학번, 이름)`과 `학생등록이력(학번, 등록시각)` 테이블이 존재한다고 가정

```sql
CREATE TRIGGER 학생_등록_기록
AFTER INSERT ON 학생
FOR EACH ROW
INSERT INTO 학생등록이력 (학번, 등록시각)
VALUES (NEW.학번, CURRENT_TIMESTAMP);
```

* 예제 해석

  * 학생 데이터가 삽입되면 등록 이력이 자동으로 저장됨

  * `NEW`: 삽입·수정 후의 행 값. `INSERT`, `UPDATE` 트리거에서 사용

  * `OLD`: 삭제·수정 전의 행 값. `DELETE`, `UPDATE` 트리거에서 사용

> 암기: 트리거 = 이벤트 발생 → 자동 실행. 프로시저 = 명시적인 호출 → 실행.

> 참고: [MySQL 공식 문서 — 트리거 문법과 예제](https://dev.mysql.com/doc/refman/8.4/en/trigger-syntax.html)
